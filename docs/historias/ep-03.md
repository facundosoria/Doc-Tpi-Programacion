# LLM-S01-H05 — Alta de golden set y carga de entradas

- **Épica:** EP-03 · Golden set y referencia humana
- **Pareja:** P5 (con P4 en la definición de rúbrica)
- **Dependencias:** H04
- **Estimación (plan):** 24 h
- **Tipo:** **Historia de usuario** (HU de valor)
- **Requisito:** RF-IA-30 a 36 (golden set y calibración)
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** docente autorizado de una cohorte
- **Quiero:** dar de alta un golden set y cargar entradas con su puntuación de referencia
- **Para:** armar la referencia humana que después calibra el evaluador de mi curso

---

## Notas / Observaciones

- **Reglas de negocio:** el alta y la carga se hacen por el Gateway (`/api/llm/**`). El servicio
  valida el **actor** (servicio de confianza + scope `llm.golden-set.manage` + usuario delegado),
  el **ownership de la cohorte** y la **idempotencia**. Cada operación de escritura exige el header
  `Idempotency-Key` (UUID) y queda registrada en auditoría.
- **Validaciones:** `transcript` es un arreglo JSON con al menos un mensaje y **no se interpreta
  como instrucciones**; `referenceScores` trae exactamente las cinco dimensiones con valores
  enteros 0–100; `language` es `es`; `rubricVersion` existe.
- **Datos obligatorios:** para el alta, `rubricVersion` y `language`; para la entrada,
  `transcript` y `referenceScores` (autonomía, claridad, progresión, cumplimiento, eficiencia).
- **Performance:** operaciones sincrónicas de baja latencia; sin llamadas a proveedores de modelo.
- **Seguridad:** un actor sin el scope requerido o una identidad no delegada por el Gateway →
  `403`; un docente que no es dueño de la cohorte → `403`; nunca se accede sin pasar por el
  Gateway.
- **Accesibilidad:** no aplica en esta historia (la pantalla es H07).
- **Otros:** el `id` del recurso creado se devuelve en el cuerpo y en el header `Location`.
- **Endpoints:**
  - `POST /api/llm/golden-sets` → `201` + `Location`; cuerpo `{ id, version, rubricVersion, language, createdAt }`.
  - `POST /api/llm/golden-sets/{goldenSetId}/entries` → `201` + `Location`; cuerpo `{ id, goldenSetId }`.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** un docente autorizado de su cohorte crea un golden set y le agrega una entrada válida;
  ambas respuestas son `201` con `Location`.
- [ ] **CA2:** repetir el mismo `POST` con la misma `Idempotency-Key` devuelve el mismo resultado sin
  crear un segundo recurso.
- [ ] **CA3 (negativo):** un docente que no es dueño de la cohorte recibe `403` y no se crea nada.
- [ ] **CA4 (negativo):** una entrada con `referenceScores` incompleto (cuatro dimensiones) o fuera de
  rango recibe `400` *Problem Details*.
- [ ] **CA5 (negativo):** una request que no pasa por el Gateway (sin headers de identidad delegada) →
  `403`.

---

## BDD

**Característica:** construcción del golden set por el docente.

### Escenario 1 — Alta y carga por el docente dueño (camino feliz)

- **Dado:** un docente autorizado sobre su cohorte, autenticado por el Gateway
- **Cuando:** crea un golden set y luego carga una entrada con transcripción y las cinco
  puntuaciones de referencia
- **Entonces:** el sistema responde `201` en ambos casos y devuelve el `id` y el `Location` de
  cada recurso
- **Y:** el golden set queda visible al consultarlo (ver [H06](#llm-s01-h06--consulta-del-golden-set-que-sobrevive-al-reinicio))

### Escenario 2 — Segunda carga con la misma Idempotency-Key

- **Dado:** una entrada ya cargada con una `Idempotency-Key` determinada
- **Cuando:** el docente reenvía exactamente el mismo `POST` con la misma clave
- **Entonces:** el sistema devuelve la misma respuesta que la primera vez y no crea una segunda
  entrada

### Escenario 3 — Docente de otra cohorte

- **Dado:** un docente autenticado que no es dueño de la cohorte del golden set
- **Cuando:** intenta crear un golden set o cargar una entrada en esa cohorte
- **Entonces:** el sistema responde `403` y no persiste ningún dato

### Escenario 4 — Puntuación de referencia incompleta

- **Dado:** el formulario de carga de entrada
- **Cuando:** el docente envía `referenceScores` con solo cuatro dimensiones
- **Entonces:** el sistema responde `400` con *Problem Details* indicando qué falta, y no crea la
  entrada

# LLM-S01-H06 — Consulta del golden set que sobrevive al reinicio

- **Épica:** EP-03 · Golden set y referencia humana
- **Pareja:** P5
- **Dependencias:** H04
- **Estimación (plan):** 14 h
- **Tipo:** **Historia de usuario** (HU de valor) · **candidata a historia canónica**
- **Requisito:** RF-IA-30 a 36 (golden set y calibración)
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** docente autorizado de una cohorte
- **Quiero:** consultar mi golden set y sus entradas aunque el servicio se reinicie
- **Para:** confiar en que el dato de referencia que cargué persiste y puedo calibrar sobre él

---

## Notas / Observaciones

- **Reglas de negocio:** la consulta se hace por el Gateway con la misma autorización que la
  escritura. El listado es paginado (`page` desde 0, `size` entre 1 y 100) y viene ordenado por
  fecha de creación descendente. El detalle incluye las entradas del golden set. Una cohorte ajena
  **no aparece** en la respuesta.
- **Validaciones:** un `goldenSetId` inexistente devuelve `404` (no `500`); un `size` fuera del
  rango 1–100 devuelve `400`.
- **Datos obligatorios:** ninguno en el cuerpo (es `GET`); parámetros `rubricVersion` (opcional),
  `page`, `size`.
- **Performance:** los datos se leen de PostgreSQL con volumen persistente; tras
  `docker compose restart` la lectura devuelve exactamente lo cargado antes.
- **Seguridad:** sin scope `llm.golden-set.manage` y usuario delegado → `403`; el filtro por
  cohorte se aplica siempre, no es un parámetro opcional.
- **Accesibilidad:** no aplica en esta historia (la pantalla es H07).
- **Otros:** esta es la **historia candidata a canónica** del backlog: pequeña, entendida por
  todos y con un recorrido completo (autorización + lectura + persistencia). Su valor en puntos se
  fija en el Sprint 0 y queda como referencia de todas las demás.
- **Endpoints:**
  - `GET /api/llm/golden-sets?rubricVersion={v}&page={n}&size={s}` → lista de
    `{ id, version, rubricVersion, language, createdAt }`.
  - `GET /api/llm/golden-sets/{goldenSetId}` → lo anterior + `entries[] { id, transcript, referenceScores, createdAt }`.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** un golden set creado y con una entrada se puede consultar y devuelve esa entrada.
- [ ] **CA2:** después de `docker compose restart`, la misma consulta devuelve los mismos datos.
- [ ] **CA3:** el listado respeta `page`/`size` y el orden por creación descendente.
- [ ] **CA4 (negativo):** el golden set de otra cohorte no aparece en el listado y su detalle responde
  `404`.
- [ ] **CA5 (negativo):** `goldenSetId` con formato UUID pero inexistente → `404` *Problem Details*,
  nunca `500`.
- [ ] **CA6 (negativo):** `size=500` → `400`.

---

## BDD

**Característica:** lectura del golden set con persistencia garantizada.

### Escenario 1 — La consulta sobrevive al reinicio (camino feliz)

- **Dado:** un docente que creó un golden set y le cargó una entrada
- **Cuando:** se ejecuta `docker compose restart` del servicio y su base
- **Y:** el docente vuelve a consultar el golden set por el Gateway
- **Entonces:** la respuesta `200` contiene el golden set y la entrada tal como se cargaron

### Escenario 2 — Aislamiento entre cohortes

- **Dado:** dos golden sets, uno de la cohorte del docente y otro de una cohorte ajena
- **Cuando:** el docente pide el listado
- **Entonces:** solo aparece el golden set de su cohorte
- **Y:** pedir el detalle del ajeno responde `404`

### Escenario 3 — Golden set inexistente

- **Dado:** un `goldenSetId` con formato válido que no corresponde a ningún golden set
- **Cuando:** el docente consulta su detalle
- **Entonces:** el sistema responde `404` con *Problem Details*, no `500`

### Escenario 4 — Paginación fuera de rango

- **Dado:** el endpoint de listado con `size` limitado a 1–100
- **Cuando:** el cliente pide `size=500`
- **Entonces:** el sistema responde `400` y no devuelve datos

# LLM-S01-H07 — Pantalla docente mínima del golden set

- **Épica:** EP-03 · Golden set y referencia humana
- **Pareja:** P5
- **Dependencias:** H05, H06
- **Estimación (plan):** 24 h
- **Tipo:** **Historia de usuario** (HU de valor)
- **Requisito:** RF-IA-30 a 36 (golden set y calibración)
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** docente
- **Quiero:** una pantalla mínima para el alta, la carga y la consulta del golden set
- **Para:** trabajar la referencia de mi curso sin depender de Swagger ni de llamadas manuales

---

## Notas / Observaciones

- **Reglas de negocio:** la pantalla (aplicación Angular `llm-workbench`) hace el alta, la carga
  de entradas y la consulta **siempre a través del Gateway**, nunca contra el servicio directo.
  Muestra la autorización vigente (quién está operando).
- **Validaciones:** la transcripción se valida como arreglo JSON no vacío antes de enviarse, con
  el aviso visible de que **no se interpreta como instrucciones**; los cinco puntajes aceptan
  0–100.
- **Datos obligatorios:** transcripción y los cinco puntajes de referencia para cargar una
  entrada.
- **Performance:** estados de carga (`aria-live`) mientras se resuelven las llamadas.
- **Seguridad:** si el backend responde `403`, la pantalla muestra ese estado de forma explícita,
  no un error genérico.
- **Accesibilidad (WCAG AA):** etiquetas asociadas a cada campo, `fieldset`/`legend` para el grupo
  de puntajes, mensajes de error con `role="alert"`, foco manejado, operable por teclado y con
  lector de pantalla.
- **Otros:** si el backend no está disponible, la pantalla muestra «no se pudo contactar al
  backend», sin romperse.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** desde la pantalla, el docente crea un golden set, carga una entrada y la ve en el
  detalle, sin usar Swagger.
- [ ] **CA2:** todas las llamadas salen hacia el Gateway (`/api/llm/**`), no al servicio directo.
- [ ] **CA3:** hay estados visibles de carga y de error en cada operación.
- [ ] **CA4 (negativo):** con el backend caído, la pantalla muestra un aviso claro y sigue navegable.
- [ ] **CA5 (negativo):** una transcripción que no es JSON válido muestra un mensaje de validación y
  **no** se envía.
- [ ] **CA6 (negativo):** una respuesta `403` del backend se refleja como «no autorizado» en la
  interfaz.

---

## BDD

**Característica:** interfaz docente mínima del golden set.

### Escenario 1 — Recorrido completo desde la pantalla (camino feliz)

- **Dado:** un docente autorizado con la pantalla abierta y el backend disponible
- **Cuando:** crea un golden set, carga una entrada con transcripción y puntajes, y abre el detalle
- **Entonces:** la entrada aparece listada con sus cinco puntajes y sus pesos

### Escenario 2 — Backend no disponible

- **Dado:** el `llm-service` detenido
- **Cuando:** el docente abre el listado de golden sets
- **Entonces:** la pantalla muestra «no se pudo contactar al backend» y no queda en blanco ni con
  un error sin contexto

### Escenario 3 — Transcripción inválida

- **Dado:** el formulario de carga de entrada
- **Cuando:** el docente pega un texto que no es un arreglo JSON y confirma
- **Entonces:** la pantalla muestra un mensaje de validación y no envía la request

### Escenario 4 — Operación no autorizada

- **Dado:** un docente cuyo backend responde `403` a la operación
- **Cuando:** intenta crear un golden set
- **Entonces:** la pantalla muestra el estado «no autorizado» con el detalle recibido
