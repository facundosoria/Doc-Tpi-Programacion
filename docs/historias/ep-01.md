# LLM-S01-H01 — ADR de arquitectura y convenciones técnicas

- **Épica:** EP-01 · Plataforma, contratos e integración

- **Dependencias:** —

---

## Descripción (Como / Quiero / Para)

- **Como:** equipo de desarrollo del `llm-service`
- **Quiero:** un ADR con el árbol de módulos y las convenciones técnicas del servicio
- **Para:** que las cinco parejas construyan sobre las mismas fronteras y decisiones

---

## Notas / Observaciones

- **Reglas de negocio:** el ADR fija Java 21, Spring Boot 3 / Maven y los límites entre paquetes
  `api` · `application` · `domain` · `infrastructure` · `security` · `configuration`. El paquete
  `domain` **no** depende de Spring, Kafka ni de SDKs de proveedores de modelos.
- **Validaciones:** las fronteras de paquete se pueden verificar de forma automática (ArchUnit) o
  en revisión de PR.
- **Datos obligatorios:** lista de variables de entorno con nombre, propósito y valor por defecto;
  decisión registrada con fecha, alternativas descartadas y responsables.
- **Performance:** no aplica.
- **Seguridad:** el ADR nombra dónde viven los secretos (fuera del repo) y cómo se inyectan.
- **Accesibilidad:** no aplica (documento interno).
- **Otros:** el ADR queda versionado en el repositorio; cambiarlo exige un nuevo ADR que supersede
  al anterior, no editar el texto.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** existe un ADR publicado y aprobado por el equipo en el repositorio, con fecha y autores.
- [ ] **CA2:** el ADR enumera los seis paquetes y la regla de dependencias entre ellos.
- [ ] **CA3:** el ADR incluye la tabla de variables de entorno del servicio.
- [ ] **CA4 (negativo):** un PR que importe Spring, Kafka o un SDK de proveedor dentro de `domain` es
  rechazado por CI o por revisión, citando el ADR.
- [ ] **CA5 (negativo):** usar una variable de entorno no listada en el ADR se marca en revisión.

---

## BDD

**Característica:** convenciones de arquitectura compartidas por todas las parejas.

### Escenario 1 — El ADR habilita el arranque parejo

- **Dado:** el ADR está aprobado y publicado en el repositorio
- **Cuando:** una pareja crea el módulo que le toca
- **Entonces:** su estructura de paquetes coincide con la del ADR y la revisión no observa desvíos

### Escenario 2 — Se protege la independencia del dominio

- **Dado:** el ADR prohíbe dependencias de framework en `domain`
- **Cuando:** un PR agrega `import org.springframework...` en una clase de `domain`
- **Entonces:** la verificación de arquitectura falla y el PR no se puede mergear

### Escenario 3 — Configuración fuera del ADR

- **Dado:** el ADR lista las variables de entorno admitidas
- **Cuando:** un cambio lee una variable de entorno que el ADR no documenta
- **Entonces:** la revisión marca la observación y pide actualizar el ADR antes de aprobar

# LLM-S01-H02 — Entorno reproducible con un comando

- **Épica:** EP-01 · Plataforma, contratos e integración
- **Pareja:** P1
- **Dependencias:** H01

- **Tipo:** Tarea / habilitador técnico
- **Requisito:** RF-NFR-03/04 (orientativo)
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** desarrollador de cualquier pareja
- **Quiero:** levantar todo el entorno local con un solo comando
- **Para:** trabajar sin instalar ni configurar dependencias a mano

---

## Notas / Observaciones

- **Reglas de negocio:** `docker compose up` deja *healthy* PostgreSQL y —según lo que pida la
  plataforma— Eureka/Gateway y Kafka. `up`, verificación de *health* y `down` están documentados.
- **Validaciones:** cada servicio del Compose define su `healthcheck`; el comando no se considera
  exitoso hasta que todos reportan *healthy*.
- **Datos obligatorios:** archivo `compose.yaml`, `.env.example` con las variables del ADR (H01),
  sección del README con los tres comandos.
- **Performance:** el entorno arranca en frío en un tiempo razonable en una notebook del equipo.
- **Seguridad:** el Compose usa credenciales de desarrollo, nunca secretos reales; el `.env` real
  está en `.gitignore`.
- **Accesibilidad:** no aplica.
- **Otros:** si falta Docker o `docker compose`, el arranque falla con un mensaje que nombra el
  requisito; no deja el entorno a medias.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** en una máquina limpia con Docker, `docker compose up` deja todos los servicios
  *healthy*.
- [ ] **CA2:** el README documenta `up`, comprobación de *health* y `down`, y funcionan.
- [ ] **CA3 (negativo):** sin Docker instalado, el comando falla con un mensaje claro que indica qué
  falta, y no arranca servicios parciales.
- [ ] **CA4 (negativo):** con un puerto requerido ya ocupado, el error identifica el puerto en
  conflicto.

---

## BDD

### Escenario 1 — Arranque en máquina limpia

- **Y:** el desarrollador puede llamar al servicio sin instalar nada más

### Escenario 3 — Puerto ocupado

- **Dado:** el puerto de PostgreSQL ya está en uso por otro proceso
- **Cuando:** el desarrollador ejecuta `docker compose up`
- **Entonces:** el arranque falla con un mensaje que nombra el puerto en conflicto

# LLM-S01-H03 — Esqueleto transversal del servicio

- **Épica:** EP-01 · Plataforma, contratos e integración
- **Pareja:** P1
- **Dependencias:** H02
- **Estimación (plan):** 34 h
- **Tipo:** Tarea / habilitador técnico
- **Requisito:** RF-NFR-01/03/04; contratos v1 (orientativo)
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** plataforma «Aprendizaje Gamificado de Programación» (equipos consumidores)
- **Quiero:** que el `llm-service` exponga su esqueleto transversal por el Gateway
- **Para:** integrar contra un borde estable antes de que existan las funciones de IA

---

## Notas / Observaciones

- **Reglas de negocio:** el servicio se registra en Eureka como `llm-service`; el Gateway rutea
  `/api/llm/**` sin reescritura de path; la seguridad M2M valida `aud=llm-service` y el scope
  requerido; los errores se devuelven como *Problem Details* (RFC 7807).
- **Validaciones:** se propaga la correlación `traceparent` y `X-Request-Id` en cada respuesta; un
  token sin el scope necesario se rechaza con `401`; una identidad delegada falsificada o mal
  formada se rechaza con `403`.
- **Datos obligatorios (headers de borde):** `X-Service-Id`, `X-Service-Scopes`,
  `X-Delegated-User`, `X-Request-Id`, `traceparent`.
- **Performance:** el *health* de Actuator responde sin llamar a proveedores externos.
- **Seguridad:** ningún endpoint funcional queda accesible sin pasar por el Gateway; los logs no
  registran tokens.
- **Accesibilidad:** no aplica.
- **Otros:** el pipeline de CI del servicio queda en verde (build, pruebas, cobertura).
- **Endpoints expuestos en esta historia:** `GET /actuator/health` (liveness/readiness) y la ruta
  base `/api/llm/**` protegida; las operaciones de golden set llegan en H05/H06.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** `llm-service` aparece registrado en Eureka y responde a través del Gateway en
  `/api/llm/**`.
- [ ] **CA2:** una request con token M2M válido (`aud=llm-service`) y scope correcto obtiene respuesta
  y recibe de vuelta su `X-Request-Id`.
- [ ] **CA3:** los errores se serializan como *Problem Details* con `type`, `title`, `status` y
  `detail`.
- [ ] **CA4 (negativo):** token sin el scope requerido → `401` *Problem Details*.
- [ ] **CA5 (negativo):** header de identidad delegada ausente o falsificado → `403`.
- [ ] **CA6:** el pipeline de CI del servicio está en verde.

---

## BDD

**Característica:** borde transversal del `llm-service`.

### Escenario 1 — Integración contra un borde estable

- **Dado:** `llm-service` registrado en Eureka y el Gateway ruteando `/api/llm/**`
- **Cuando:** un servicio consumidor llama con token M2M válido y scope correcto
- **Entonces:** recibe una respuesta del servicio
- **Y:** la respuesta incluye el mismo `X-Request-Id` que envió

### Escenario 2 — Token sin scope

- **Dado:** un servicio consumidor con un token M2M válido pero sin el scope requerido
- **Cuando:** llama a una ruta `/api/llm/**`
- **Entonces:** recibe `401` con cuerpo *Problem Details*

### Escenario 3 — Identidad delegada falsificada

- **Dado:** una request que trae un `X-Delegated-User` que no vino del Gateway de confianza
- **Cuando:** llega al servicio
- **Entonces:** se rechaza con `403` y no se ejecuta ninguna acción

---

- **Capturas:** no aplica (borde técnico).
- **Mock API / Swagger:** `GET /actuator/health`; contrato base en [`contracts/llm-service-v1.openapi.yaml`](../contracts/llm-service-v1.openapi.yaml).

- **Servicios involucrados:** Gateway, Eureka, emisor de tokens M2M.
- **Módulos afectados:** `api`, `security`, `configuration`.
- **Otros equipos / aprobaciones:** equipo de Gateway/Discovery (D01): ruta, `aud` y scopes.

# LLM-S01-H04 — Esquema inicial versionado con auditoría

- **Épica:** EP-01 · Plataforma, contratos e integración
- **Pareja:** P1
- **Dependencias:** H03
- **Estimación (plan):** 38 h
- **Tipo:** Tarea / habilitador técnico
- **Requisito:** RF-IA-30 a 36 (golden set y calibración); RF-NFR-01
- **Referente de producto:** *(a nombrar en Sprint 0)*

---

## Descripción (Como / Quiero / Para)

- **Como:** plataforma (dueña del dato académico)
- **Quiero:** el esquema inicial del `llm-service` versionado con migraciones
- **Para:** que el dato de referencia nazca con auditoría y sin edición destructiva

---

## Notas / Observaciones

- **Reglas de negocio:** una migración Flyway (`V1`) desde base vacía crea la rúbrica de
  plataforma **1.0** con sus **cinco dimensiones** y pesos (autonomía 30, claridad 25, progresión
  20, cumplimiento 15, eficiencia 10), y las tablas de golden set, entrada, idempotencia y
  auditoría.
- **Validaciones:** las tablas de dato académico son *append-only* — un `UPDATE` o `DELETE`
  destructivo se rechaza a nivel base. Una puntuación de referencia incompleta (menos de las cinco
  dimensiones) o fuera de rango (0–100) se rechaza. El índice de idempotencia es único por
  `(operación, servicio, usuario delegado, Idempotency-Key)`.
- **Datos obligatorios:** versión de rúbrica, idioma (`es`), definición de dimensiones y pesos.
- **Performance:** la migración corre en segundos sobre base vacía y es reproducible.
- **Seguridad:** la auditoría guarda actor (servicio + usuario), recurso, `X-Request-Id` y
  `traceparent`; no guarda transcripciones como texto libre interpretable.
- **Accesibilidad:** no aplica.
- **Otros:** cambiar la rúbrica exige una versión nueva, no editar la 1.0.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** Flyway sobre una base vacía deja creadas las tablas de rúbrica, dimensiones, golden
  set, entrada, idempotencia y auditoría, y la rúbrica 1.0 con sus cinco dimensiones y pesos.
- [ ] **CA2:** la migración es reproducible: correrla de nuevo desde cero da el mismo resultado.
- [ ] **CA3 (negativo):** un `UPDATE` o `DELETE` sobre una tabla *append-only* falla con un error que
  dice que la tabla no admite cambios.
- [ ] **CA4 (negativo):** insertar una entrada con cuatro dimensiones, o con un score de 120, se
  rechaza por restricción de la base.
- [ ] **CA5 (negativo):** dos registros de idempotencia con la misma clave para la misma operación,
  servicio y usuario no pueden coexistir.

---

## BDD

**Característica:** esquema académico versionado e inmutable.

### Escenario 1 — Migración desde base vacía

- **Dado:** una base de datos PostgreSQL vacía
- **Cuando:** el servicio arranca y Flyway aplica la migración `V1`
- **Entonces:** existen las tablas del golden set y la rúbrica 1.0 con sus cinco dimensiones y pesos

### Escenario 2 — La tabla no admite edición destructiva

- **Dado:** un golden set ya persistido
- **Cuando:** alguien ejecuta `UPDATE golden_sets ...` o `DELETE FROM golden_sets ...`
- **Entonces:** la base rechaza la operación indicando que la tabla es *append-only*

### Escenario 3 — Puntuación de referencia inválida

- **Dado:** la restricción de que una entrada tiene las cinco dimensiones con valores 0–100
- **Cuando:** se intenta insertar una entrada con solo cuatro dimensiones (o un valor 120)
- **Entonces:** la inserción se rechaza por restricción y no queda registro

---

## Prototipo

- **Capturas:** diagrama entidad-relación de las tablas creadas (adjuntar en Taiga; ver
  [12 · Almacenamiento e ingesta](../12-almacenamiento-e-ingesta.md)).
- **Mock API / Swagger:** no aplica (capa de datos).

---

## Estimación / Prioridad

| Puntos (Fibonacci) | Prioridad (MoSCoW) |
|---|---|
| *(a asignar en Sprint 0)* | Must |

- **Servicios involucrados:** PostgreSQL.
- **Módulos afectados:** `infrastructure` (persistencia y migraciones), `domain` (invariantes).
- **Otros equipos / aprobaciones:** definición docente de las cinco dimensiones y pesos (D02).
- **Impacto en datos / migraciones:** crea el esquema base; todas las historias siguientes

## Notas / Observaciones

- **Reglas de negocio:** la suite cubre unitarias de reglas de dominio, integración de
  persistencia y migración con Testcontainers/Flyway, contrato del Gateway con WireMock y la
  prueba de **reinicio de Compose**. La cobertura cumple el umbral de [24](../24-convenciones-cobertura.md)
  (95 % back/front).
- **Validaciones:** los **escenarios BDD de aceptación** de H05–H07 (camino feliz + negativos)
  quedan ejecutados con evidencia.
- **Datos obligatorios:** guía de demo paso a paso: acceso autorizado → alta → carga → consulta
  tras reinicio.
- **Performance:** la suite corre en CI en un tiempo acotado.
- **Seguridad:** se prueban los casos de autorización (`401`/`403`) y de idempotencia.
- **Accesibilidad:** el front incluye pruebas de componente; las verificaciones de accesibilidad
  de H07 se listan en la guía.
- **Otros:** la guía de demo es ejecutable por cualquier integrante en un ambiente integrado, no
  en una máquina local aislada.

## Criterios de Aceptación (CA)

- [ ] **CA1:** la suite completa corre en verde en CI.
- [ ] **CA2:** la cobertura back y front alcanza el umbral de [24](../24-convenciones-cobertura.md).
- [ ] **CA3:** existe una prueba automatizada que reinicia Compose y verifica que el golden set
  persiste.
- [ ] **CA4:** la guía de demo se puede seguir paso a paso y termina en la consulta tras reinicio.
- [ ] **CA5 (negativo):** si la cobertura baja del umbral, CI falla el PR.
- [ ] **CA6 (negativo):** si la prueba de reinicio detecta pérdida de datos, falla y bloquea la
  Review.

## BDD

**Característica:** evidencia reproducible del incremento de S1.

### Escenario 1 — La suite valida el incremento (camino feliz)

- **Dado:** el código de S1 integrado
- **Cuando:** CI ejecuta la suite completa
- **Entonces:** todas las pruebas pasan y la cobertura queda por encima del umbral de [24](../24-convenciones-cobertura.md)

### Escenario 2 — Cobertura insuficiente

- **Dado:** un PR que agrega código sin pruebas
- **Cuando:** CI mide la cobertura
- **Entonces:** la cobertura cae bajo el umbral y CI marca el PR como fallido

### Escenario 3 — Pérdida de datos en el reinicio

- **Dado:** la prueba automatizada de reinicio de Compose
- **Cuando:** tras el reinicio el golden set cargado antes no está
- **Entonces:** la prueba falla y la Review no puede aceptar el incremento
