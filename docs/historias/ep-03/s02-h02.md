## Descripción (Como / Quiero / Para)

- **Como:** docente autorizado de un curso
- **Quiero:** crear el golden set de mi curso —copiando la versión base que publicó la
  plataforma, o armándolo desde cero—, cargarle casos y publicar versiones sucesivas
- **Para:** tener mi propia referencia de curso, trazable y versionada, sin que mis cambios
  afecten la base de la plataforma ni ninguna versión que ya publiqué

---

## Notas / Observaciones

- **Reglas de negocio:** un golden set de curso nace como borrador (`DRAFT`), ya sea vacío
  (`createDraft`) o **copiado de una versión base publicada por la plataforma**
  (`copyFromPublishedBase`). Cada caso cargado incluye la transcripción (arreglo con al menos
  un mensaje), el contexto del desafío, el autor y las cinco puntuaciones de referencia
  (0–100 cada una). Publicar (`DRAFT → PUBLISHED`) lo deja inmutable — igual que la rúbrica,
  reforzado por un trigger de base de datos, no solo por la aplicación.
- **Anonimización real:** antes de guardar cualquier caso (cargado a mano o importado), la
  transcripción y la metadata pasan por un anonimizador que quita campos como
  `student_id`/`email` y sanitiza el texto libre. No es una promesa de diseño: está en el
  código (`RealCaseAnonymizer`), aplicado siempre, no opcional.
- **Importación masiva:** además de cargar casos uno por uno, existe un flujo de importación
  por lotes (JSON o CSV) con **validación fila por fila** (transcripción, contexto, autor y
  las cinco puntuaciones) y un **commit atómico**: solo se insertan los casos si todas las
  filas del lote quedaron válidas.
- **Borrado controlado:** un borrador sin usar se puede eliminar (baja lógica). Un golden set
  ya publicado, calibrado, o vinculado a un desafío/examen/intento **no se puede borrar**.
- **⚠️ Hueco abierto — origen de la base de plataforma.** `copyFromPublishedBase` **lee** una
  versión de plataforma ya publicada (`scope = 'PLATFORM'`), pero en esta revisión no se
  encontró ningún endpoint que **cree** esa base de plataforma — solo existe el flujo por
  curso. Hay que confirmar con quien mantiene el módulo si falta ese endpoint, si se siembra
  de otra forma (migración, script), o si la base de plataforma no es responsabilidad de esta
  historia.
- **Validaciones:** las cinco puntuaciones de referencia, cada una 0–100; transcripción no
  vacía; nombre obligatorio al crear un borrador.
- **Performance:** sin llamadas a un modelo; lectura/escritura directa contra PostgreSQL.
- **Seguridad:** igual que la rúbrica — solo un docente autorizado **de ese curso** opera;
  cualquier otro recibe **403**.
- **Accesibilidad:** no evaluado en esta revisión.
- **Otros:** el perfil `workbench` de desarrollo local evita esta autorización real — no usarlo
  para una demo en ambiente integrado.

## Criterios de Aceptación (CA)

- [ ] **CA1:** un docente autorizado de su curso crea un golden set (vacío o copiado de una
  base publicada de plataforma) y le agrega un caso válido.
- [ ] **CA2:** publicar un golden set con al menos un caso lo deja `PUBLISHED` e inmutable;
  ningún cambio posterior tiene efecto.
- [ ] **CA3:** los datos de alumno de cada caso (transcripción, metadata) llegan anonimizados
  a la base, tanto cargados a mano como importados por lote.
- [ ] **CA4 (negativo):** un docente que no pertenece al curso recibe **403** en cualquier
  operación.
- [ ] **CA5 (negativo):** un caso con puntajes de referencia incompletos o fuera de 0–100 se
  rechaza, cargado a mano o por importación.
- [ ] **CA6 (negativo):** intentar borrar un golden set ya publicado, calibrado o vinculado a
  un desafío se rechaza, explicando el motivo.
- [ ] **CA7 (negativo):** un lote de importación con al menos una fila inválida no comitea
  ningún caso hasta que todas las filas queden válidas.

## BDD

**Característica:** golden set de curso versionado, con datos de alumno siempre anonimizados.

### Escenario 1 — Copiar la base de plataforma y publicar (camino feliz)

- **Dado:** un docente autorizado de su curso y una versión base de plataforma ya publicada
- **Cuando:** copia esa base a su curso, agrega un caso con transcripción y los cinco puntajes,
  y publica
- **Entonces:** el golden set del curso queda `PUBLISHED`, con el caso incluido, sin afectar la
  base de plataforma original

### Escenario 2 — Anonimización real de un caso cargado

- **Dado:** un caso cuya transcripción menciona el nombre y el mail del alumno
- **Cuando:** el docente lo carga
- **Entonces:** lo que queda guardado no contiene esos datos identificatorios

### Escenario 3 — Importación con una fila inválida

- **Dado:** un lote de importación con 3 filas, una de ellas con puntajes fuera de rango
- **Cuando:** el docente valida y comitea el lote
- **Entonces:** la validación marca la fila inválida y el commit no inserta ningún caso hasta
  corregirla

### Escenario 4 — Borrado de un golden set en uso

- **Dado:** un golden set ya vinculado a una calibración
- **Cuando:** el docente intenta eliminarlo
- **Entonces:** el sistema rechaza el borrado y explica que está en uso

## Dependencias / Impactos

- **Servicios involucrados:** Gateway, PostgreSQL.
- **Módulos afectados:** `api`, `application`, `domain`, `infrastructure` de `llm-service`;
  pantallas de golden set de `llm-workbench`.
- **Otros equipos / aprobaciones:** confirmar el hueco de la base de plataforma (ver nota
  arriba) con quien mantiene el módulo.
- **Impacto en datos / migraciones:** tablas `golden_set_families`, `golden_set_versions`,
  `golden_set_cases`, `import_batches`, `import_rows` (migración `V2` y siguientes),
  inmutabilidad reforzada por trigger.
- **Riesgos y mitigación:** si nadie crea la base de plataforma, `copyFromPublishedBase` no
  tiene qué copiar y todo curso debe partir desde cero — se mitiga resolviendo el hueco antes
  de comprometer esta historia en un sprint.
