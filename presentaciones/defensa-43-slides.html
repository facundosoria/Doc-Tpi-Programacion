Visión General

Resumen Ejecutivo

Esta propuesta presenta la arquitectura técnica y la estrategia de integración de Inteligencia Artificial para la Plataforma Gamificada de la UTN FRC. El módulo de IA se despliega como un microservicio autónomo que expone REST/SSE, separando completamente la responsabilidad de inferencia de las decisiones de negocio del core académico. La plataforma atiende a los requerimientos RF-IA-01 a través RF-IA-36 del PRD, cubriendo asistencia socrática, evaluación con rúbrica fija, filtros anti-fuga, calibración con golden set y gobernanza multi-modelo.

La regla de oro que atraviesa toda la arquitectura es clara: el microservicio de IA ejecuta inferencia y expone datos; el core toma decisiones de negocio. Esta separación de responsabilidades mantiene los límites de servicio limpios, permite reemplazar piezas sin romper el sistema y garantiza que la IA sea un amplificador pedagógico y no un motor de decisión. El microservicio no lee la base de datos del core; recibe todo el contexto por request o consulta endpoints del core, respetando los contratos estrictos definidos en el PRD.

Regla de Oro

El microservicio de IA no calcula valores de XP, no decide transiciones de estado de cursos, no modifica notas y no accede a la base de datos del core. Expone datos e inferencia; el core consume esos datos y decide. Si mañana cambia la economía del juego (PAR-05) o la lógica de activación (RF-IA-36), el microservicio no se entera ni le importa.

Síntesis del Proyecto

Los siete hallazgos que ordenan todo el trabajo

1
El alcance oficial es más angosto de lo que asumíamos

El Tema 07 son seis cosas: rúbrica, invocación del modelo, golden set, calibración, bloqueo de activación y salvaguarda anti-fuga. El RAG, el tutor y el generador no están asignados a ningún equipo.

2
Pero la salvaguarda anti-fuga nos pone en el camino del tutor

Corre sobre la respuesta del tutor justo antes de que el alumno la vea: no se puede ser dueño de ese guardarraíl sin estar ahí. Y sin tutor no hay transcripción, así que el evaluador se queda sin insumo.

3
El costo es de USD 5 a 22 por cuatrimestre

Y la palanca principal no es qué modelo elegís, es cuántos tokens le mandás: recortar el contexto del tutor de 6.000 a 3.000 ahorra más que cambiar de modelo, sin costar calidad.

4
Entre el 45% y el 60% de la rúbrica se calcula con código

No por ahorro: por reproducibilidad, inmunidad a prompt injection, auditabilidad y ausencia de deriva entre corridas.

5
RF-IA-20 mata el streaming token a token

En desafíos prácticos no se puede bloquear una respuesta que el alumno ya está leyendo. De ahí el buffer AST.

6
El golden set es el ítem de plazo más largo y no depende de nadie técnico

Sin calibración aprobada, ningún curso pasa de borrador a activo — sin override, ni de ADMIN.

7
La herramienta de carga del golden set tiene que existir antes

Parece «una pantalla de admin más» y en realidad destraba el camino crítico: sin ella el trabajo docente no puede ni empezar.

Los siete salen de la documentación de trabajo, no de la teoría: cada uno cambió una decisión de diseño y quedó registrado como ADR en docs/08.

¿Por qué no podemos usar ChatGPT comercial en la universidad?

Chatbots Comerciales Estándar

Entrenados para complacer, no para enseñar

Los LLMs comerciales aplican RLHF (*Reinforcement Learning from Human Feedback*) para entregar la respuesta más rápida y complaciente. Frente a un error de código, proporcionan la solución 100% resuelta.

Varianza No Determinística: Dos ejecuciones idénticas devuelven notas discrepantes (ej. 65 vs 90) por falta de temperatura 0 y semilla fija.

Integración · Frontera

Los tres «gateway» que se dicen igual

Es la confusión más cara de la integración: las tres cosas se dicen «gateway», las tres aparecen en el mismo diagrama y hacen cosas distintas.

Cuál Qué hace Dónde vive Quién lo decide
nginx (borde) Sirve el Angular compilado, termina TLS, hace de reverse proxy hacia adentro Delante de todo Infraestructura compartida
API Gateway Única puerta a los microservicios. Valida el token, propaga contexto, resuelve instancia contra Service Discovery Entre nginx y los servicios Cátedra: no negociable
AI Gateway (M1) Envuelve toda llamada a un LLM: cuota, guardarraíles, adapter, reintento, registro. No rutea tráfico HTTP entrante Adentro de ms-evaluacion-llm Nosotros: es diseño interno
Las tres flechas que importan son las que no están.
nginx nunca toca a ms-evaluacion-llm; el API Gateway nunca sabe que existe un LLM; y el AI Gateway nunca recibe una petición de afuera.
La U1 de Front End enseña nginx como gateway de microservicios, con un location por servicio. Aplicado literal acá, un proxy_pass hacia nuestro servicio abriría una segunda puerta que no valida el token. No se contradicen: nginx es el borde, el gateway es el ruteo. Registrado en ADR-015.
Investigación • Spring AI

Primitivas Clave de Spring AI

Spring AI 1.0.0 (GA, mayo 2025) es la capa de abstracción que permite al microservicio comunicarse con modelos LLM de múltiples proveedores sin acoplarse a ningún SDK propietario. Requiere Spring Boot 3.4.x como versión mínima compatible. Spring AI no es una capa de lógica de negocio: no decide qué score asignar, qué curso activar ni qué modelo calibra. Proporciona el cómo llamar al modelo, no el óqué hacer con la respuesta.

ChatClient

Interfaz unificada para hablar con cualquier LLM compatible con API OpenAI. Abstrae la llamada con configuración por YAML: base-url, api-key, modelo. Cambiar de proveedor implica cambiar configuración, no código Java. Habilita el agnosticismo de proveedor (RF-IA-11).

RF-IA-11

BeanOutputConverter

Fuerza al modelo a devolver JSON con esquema exacto y lo convierte automáticamente a un record de Java validado con Spring Validation (@Min, @Max, @NotNull). Utilizado por el EvaluadorService para parsear el score 5D y el desglose por dimensión sin parsing manual.

RF-IA-13/15

Advisors API

Hook de interceptación que se registra en el pipeline del tutor. El AntiFugaAdvisor envuelve la llamada al LLM: verifica similitud de código contra la solución esperada y regenera si supera el 70% (PAR-11). Es la red de seguridad determininástica que no depende del comportamiento del modelo.

RF-IA-20

ChatMemory

Gestiona el historial conversacional con chronología estricta de mensajes y timestamps de milisegundos. Alimenta al Evaluador y a la auditoría. Cada interacción alumno-IA se registra con snapshot del código, cumpliendo RF-IA-02 de registro absoluto.

RF-IA-02

Embeddings + VectorStore

Pipeline RAG: chunking de PDFs del profesor, generación de embeddings y almacenamiento vectorial en pgvector. En consulta: búsqueda semántica de fragmentos relevantes inyectados en el prompt. Se implementa en Fase 3, dejando la puerta abierta desde el diseño actual.

Fase 3

Function Calling

Permite al modelo invocar herramientas determinísticas como el PorteroService (clasificación de intención off-topic) y el filtro de categorías del Moderador. En Fase 2 habilita el agente moderador de chat con clasificación multi-etiqueta.

Regla de Separación de Responsabilidades

La columna "Donde vive la decisión de negocio" nunca puede ser el modelo de IA. La lógica de negocio — transiciones de estado, bloqueos sin override, economía de XP, cálculo de ponderaciones — vive en el core o en los módulos Java de nuestro microservicio (anti-fuga determinístico con JavaParser, scoring 5D, cuotas con Redis). Spring AI apenas habilita la comunicación con el modelo; nunca reemplaza la toma de decisiones.

Flujos

Flujos de Comunicación: REST/SSE vs AMQP

Existen dos flujos de comunicación inter-servicios que reflejan dos naturalezas distintas de operación: el tutor socrático operado en streaming síncrono sobre SSE para latencia interactiva (<800ms), y el evaluador analítico operado asíncronamente sobre AMQP para procesamiento batch de alta integridad. La elección de protocolo no es decorativa: determina las garantías de entrega, la tolerancia a fallos y el modelo de responsabilidad entre microservicio y motor de desafíos.

1. Tutor Socrático en Streaming (SSE) Síncrono

El alumno escribe en el IDE Monaco y espera una respuesta en tiempo real. La respuesta debe fluir letra por letra para mantener la ilusión de un tutor presente.

  1. 1. Frontend llama a Gateway (:8080) POST /ai/tutor
  2. 2. Gateway resuelve en Eureka y rutea al Microservicio ms-evaluacion-llm (:8081)
  3. 3. Spring Boot valida cuota en Redis y ejecuta filtros determinísticos (<1ms)
  4. 4. Spring AI llama al modelo (Gemini Flash) y pasa por Buffer AST JavaParser
  5. 5. Stream SSE fluye hacia Monaco Editor en vivo (<800ms TTFT)
2. Evaluación Analítica Forense (5D) Asíncrono

El alumno entrega el desafío y la evaluación ocurre en background. No hay interacción humana esperada; la integridad del score es prioritaria sobre la latencia.

  1. 1. Alumno entrega ejercicio en Motor de Desafíos
  2. 2. Motor publica en RabbitMQ: student.challenge.submitted
  3. 3. Spring RabbitListener consume la cola de evaluaciones asíncronas
  4. 4. Service ejecuta Scoring Híbrido (código determinístico + Claude Haiku T=0)
  5. 5. Persiste en scores_ia y publica ai.evaluation.completed
Atomicidad de la Economía

Dos escritores sobre la economía (IA y Motor de Desafíos) generarían condiciones de carrera. La IA solo emite métricas pedagógicas. El evento AMQP ai.evaluation.completed es el puente entre el mundo de la evaluación y la modificación de XP que realiza el Motor de Desafíos con el factor PAR-05 (±20%).

  2. Evaluador consume cola AMQP → Buffer JavaParser valida código

  4. Scoring 5D ejecuta evaluación con 5 dimensiones (45-60% código)

  2. ast.parse() analiza el árbol sintáctico

  4. Escape XML delimitación de contenido
  5. Respuesta genérica al alumno sin exposición

  2. Evaluador ejecuta scoring contra respuestas esperadas
  3. DRIFT calcula desviación porcentual
  4. PAR-14 verifica tolerancia ±5%
  5. Alerta a ADMIN si excede → recalibración automática

Ejemplo: Golden set 20 items → 18 correctos (90%) → dentro de tolerancia. Si 15 correctos (75%) → alerta de deriva.

El Fallo de Diseño en Instruction Fine-Tuning

En software tradicional, las instrucciones de control y los datos de usuario viajan en canales y tipos separados (*Prepared Statements* en SQL).

En los LLMs, tanto el System Prompt del docente como el Input del alumno son cadenas de texto plano idénticas. El modelo procesa todo como un único flujo secuencial de tokens y no posee separación de memoria por hardware.

Capa 5: Buffer Interceptor AST con JavaParser

¿Por qué el Matching de Texto Plano Falla?

Un filtro tradicional por cadenas falla si el LLM renombra variables (`x` por `contador`), altera la indentación o introduce comentarios.

La librería JavaParser extrae el esqueleto estructural de nodos del compilador, abstrayendo el código a su forma pura:

CompilationUnit → MethodDeclaration → ForStmt → IfStmt → ReturnStmt

Se calcula la similitud con LevenshteinDistance sobre la secuencia normalizada de nodos AST. Si es ≥ 70% (PAR-11), se neutraliza la respuesta y se emite un desvío pedagógico.

AntiFugaAdvisor.java Java 21 (Spring AI Advisor) 
@Component
public class AntiFugaAdvisor implements CallAroundAdvisor {
    @Autowired private JavaParserAstMatcher astMatcher;

    @Override
    public AdvisedResponse aroundCall(AdvisedRequest req, Chain chain) {
        AdvisedResponse resp = chain.nextAroundCall(req);
        String tutorOutput = resp.response().getResult().getOutput().getContent();
        double sim = astMatcher.calcularSimilitud(tutorOutput, req.getSolutionCode());
        if (sim >= 0.70) { // PAR-11 Bloqueo Anti-Fuga
            return AdvisedResponse.from(resp)
                .withOutput("> 💡 [Pista reservada: intenta plantear el algoritmo]")
                .build();
        }
        return resp;
    }
}

El gate de calidad: qué problema resuelve, y cuál no

No es una herramienta, es un orden: una cadena de verificaciones donde la primera que falla corta el resto.

Los cuatro problemas que resuelve

Alguien rompe dev. Somos seis sobre el mismo servicio. El caso típico no es el error de tipeo: es que cambiaste una firma y rompiste una clase que no abriste.
Cada IDE está configurado distinto. No hay forma de verificar el IntelliJ de otro. El contenedor sí es verificable, porque es del repo.
La documentación se desincroniza sola. 15 documentos con 173 links internos. Ya encontró 22 anclas rotas que nadie había notado.
El error llega sin la solución. Un log de Maven corrido no dice qué hacer. Cada hallazgo trae dónde, por qué y cómo se arregla.

Lo que NO resuelve

  • • No valida que lo que escribiste tenga sentido. Si calculás mal el score de la rúbrica, todo pasa en verde. Un gate verifica forma, no verdad.
  • • No reemplaza el code review. Es un piso, no un techo.
  • • Un gate mal calibrado es peor que ninguno, porque genera confianza que no corresponde.

La regla de operación

Ninguna regla nace en bloquea: nace en avisa. Se la deja avisando una o dos semanas, se mira qué encuentra sobre trabajo real, y se la sube recién cuando demuestre que los hallazgos son ciertos.

El riesgo real no es que se filtre un error de tipeo. Es que a la tercera semana todos pusheen con el gate desactivado.

A continuación se detallan los cuatro riesgos principales del proyecto, su probabilidad de ocurrencia, su impacto potencial sobre la plataforma y la mitigación correspondiente basada en los mecanismos de resiliencia y gobernanza ya definidos en la arquitectura.

Riesgo: Falla de proveedor LLM Alto

Uno o más proveedores cloud (Groq, Cerebras, Gemini) quedan indisponibles durante un horario de alta demanda.

Probabilidad: Media · Impacto: Alto

Mitigación: Cascada de proveedores con fallback automático (RF-IA-27). Si el proveedor primario falla, se intenta el siguiente. Si todos fallan: el tutor responde sin asistencia (factor IA = 1.0 neutro) y la evaluación queda en cola diferida.

Riesgo: Drift del evaluador Medio

El proveedor cloud actualiza silenciosamente los pesos de su modelo. Un LLM que hoy califica con 80 podría mañana calificar con 65 la misma entrega.

Probabilidad: Media · Impacto: Alto

Mitigación: DriftJob mensual (Celery Beat) que re-evalía el golden set y calcula el MAE. Si MAE > 5.0 (PAR-14), activa bandera de emergencia en Redis y bloquea evaluaciones con HTTP 503.

Riesgo: Fuga de código Alto

El tutor genera código con similitud ≥70% contra la solución esperada, violando PAR-11 y entregando la solución al alumno.

Probabilidad: Baja · Impacto: Crítico

Mitigación: Triple defensa: (1) System prompt condicionado por riesgo, (2) AntiFugaService con Levenshtein + comparación AST, (3) AntiFugaAdvisor que intercepta y regenera hasta 2 reintentos. Es red de seguridad determinística.

Riesgo: Calibración no aprobada Medio

El docente no produce el golden set de su curso o la calibración no pasa PAR-14 antes de la fecha de inicio.

Probabilidad: Media · Impacto: Alto

Mitigación: CRON del core que revisa cursos en draft próximos a iniciar sin calibración y dispara notificaciones (RF-NOT-02) con una semana de margen. Sin override: el curso no se activa sin calibración aprobada (RF-IA-36).

Plan de Contingencia

Si el evaluador está caído: se acepta la entrega, se otorga XP base y el ID de sesión entra en evaluaciones_pendientes. El job procesa la cola cada 60 segundos con backoff implícito. Si después de 5 intentos sigue fallando, se marca como error. El score diferido se aplica antes del cierre del curso; si el cierre ya ocurrió, el sistema responde 409 Conflict. La IA es un amplificador, no el motor core: el motor core es la evaluación técnica del código.

ADR-008: Mínima Exposición

La solución oficial nunca entra al prompt del tutor. Ningún exploit dentro de un PDF puede exfiltrar lo que no existe en la memoria de contexto.

Principio: mínimo privilegio

Los agentes de IA no ejecutan shell ni tienen acceso a BD de usuarios. Aunque un atacante logre jailbreak, el blast radius está contenido.

Regla Fundamental de Responsabilidad

El microservicio de IA informa y ejecuta inferencia. El core consume datos y toma decisiones de negocio. La calibración de RF-IA-36 es bloqueante sin override: el core consulta el estado del microservicio y bloquea la transición draft→activo si no está aprobada. Ni el ADMIN puede autorizar el arranque con el set base como reemplazo.

El principio del reparto

Cada persona arranca con una pieza que no depende de nadie, y su segunda tarea reusa lo que construyó en la primera.

Evita las dos cosas que matan a un equipo de seis en un TP: que cinco esperen a que uno termine, y que nadie pueda tocar el código de otro porque no lo entiende.

Cada módulo es una carpeta

Con una interfaz explícita — no un microservicio. Las ocho piezas comparten gateway, guardarraíles, cuotas y log: separarlas en servicios multiplicaría la maquinaria transversal sin comprar nada.

Cerradas, con fundamento

Java Spring Boot para el servicio. La materia es de Java y la integración con Spring Cloud pesa más que el ecosistema de IA de Python.
Un microservicio, no cinco. Las cinco funciones comparten gateway, guardarraíles, cuotas y log.
Sin orquestador basado en LLM. La ruta la sabe la UI. Un router agrega latencia, costo, un punto de falla y superficie de injection.
Sincrónico solo para tutor y moderador. El resto va por cola: Batch al 50% y el pico absorbido.
La solución de referencia nunca entra al contexto del tutor. No se puede filtrar lo que no se tiene.
El perímetro temático lo hace cumplir el retrieval, no el prompt. Una instrucción se sortea hablando; un filtro en el servidor no.

Qué se unificó, y con qué criterio

Cuatro ramas entraron en una. Donde el mismo documento existía dos veces, quedó la versión más nueva: quince archivos eran copias byte a byte de versiones anteriores y se descartaron.

Las equivalencias de nombre viejo → nuevo están en docs/importado/CORRECCIONES-SUGERIDAS.md, para que nadie se quede buscando un archivo que sí está, con otro nombre.

El material de otros equipos entró sin tocar

Cada archivo importado es byte a byte idéntico a su rama de origen, y la carpeta lleva el nombre de quien lo escribió. Lo que había que corregir quedó anotado en un CORRECCIONES-SUGERIDAS.md por carpeta, no aplicado.

Y queda fuera de owned-paths.txt: el gate lo reporta como informativo y nunca bloquea por él. Es el mismo mecanismo que va a permitir convivir con los otros diez equipos en el monorepo.
