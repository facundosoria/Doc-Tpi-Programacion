Visión General

Resumen Ejecutivo

Esta propuesta presenta la arquitectura técnica y la estrategia de integración de Inteligencia Artificial para la Plataforma Gamificada de la UTN FRC. El módulo de IA se despliega como un microservicio autónomo que expone REST/SSE, separando completamente la responsabilidad de inferencia de las decisiones de negocio del core académico. La plataforma atiende a los requerimientos RF-IA-01 a través RF-IA-36 del PRD, cubriendo asistencia socrática, evaluación con rúbrica fija, filtros anti-fuga, calibración con golden set y gobernanza multi-modelo.

La regla de oro que atraviesa toda la arquitectura es clara: el microservicio de IA ejecuta inferencia y expone datos; el core toma decisiones de negocio. Esta separación de responsabilidades mantiene los límites de servicio limpios, permite reemplazar piezas sin romper el sistema y garantiza que la IA sea un amplificador pedagógico y no un motor de decisión. El microservicio no lee la base de datos del core; recibe todo el contexto por request o consulta endpoints del core, respetando los contratos estrictos definidos en el PRD.

Regla de Oro

El microservicio de IA no calcula valores de XP, no decide transiciones de estado de cursos, no modifica notas y no accede a la base de datos del core. Expone datos e inferencia; el core consume esos datos y decide. Si mañana cambia la economía del juego (PAR-05) o la lógica de activación (RF-IA-36), el microservicio no se entera ni le importa.

Investigación • Spring AI

Primitivas Clave de Spring AI

Spring AI 1.0.0 (GA, mayo 2025) es la capa de abstracción que permite al microservicio comunicarse con modelos LLM de múltiples proveedores sin acoplarse a ningún SDK propietario. Requiere Spring Boot 3.4.x como versión mínima compatible. Spring AI no es una capa de lógica de negocio: no decide qué score asignar, qué curso activar ni qué modelo calibra. Proporciona el cómo llamar al modelo, no el óqué hacer con la respuesta.

ChatClient

Interfaz unificada para hablar con cualquier LLM compatible con API OpenAI. Abstrae la llamada con configuración por YAML: base-url, api-key, modelo. Cambiar de proveedor implica cambiar configuración, no código Java. Habilita el agnosticismo de proveedor (RF-IA-11).

RF-IA-11

BeanOutputConverter

Fuerza al modelo a devolver JSON con esquema exacto y lo convierte automáticamente a un record de Java validado con Spring Validation (@Min, @Max, @NotNull). Utilizado por el EvaluadorService para parsear el score 5D y el desglose por dimensión sin parsing manual.

RF-IA-13/15

Advisors API

Hook de interceptación que se registra en el pipeline del tutor. El AntiFugaAdvisor envuelve la llamada al LLM: verifica similitud de código contra la solución esperada y regenera si supera el 70% (PAR-11). Es la red de seguridad determininástica que no depende del comportamiento del modelo.

RF-IA-20

ChatMemory

Gestiona el historial conversacional con chronología estricta de mensajes y timestamps de milisegundos. Alimenta al Evaluador y a la auditoría. Cada interacción alumno-IA se registra con snapshot del código, cumpliendo RF-IA-02 de registro absoluto.

RF-IA-02

Embeddings + VectorStore

Pipeline RAG: chunking de PDFs del profesor, generación de embeddings y almacenamiento vectorial en pgvector. En consulta: búsqueda semántica de fragmentos relevantes inyectados en el prompt. Se implementa en Fase 3, dejando la puerta abierta desde el diseño actual.

Fase 3

Function Calling

Permite al modelo invocar herramientas determinísticas como el PorteroService (clasificación de intención off-topic) y el filtro de categorías del Moderador. En Fase 2 habilita el agente moderador de chat con clasificación multi-etiqueta.

RF-IA-05/F2
Nota de Versiones

Spring AI 1.0.0 GA (mayo 2025) requiere Spring Boot 3.4.x o superior. Si el proyecto está fijado en Spring Boot 3.3.x, debe usarse Spring AI 1.0.0-M6 o actualizar Spring Boot. El stack declarado es: Java 21 · Spring Boot 3.4.x · Maven · PostgreSQL 16+ · Spring AI 1.0.0.

Regla de Separación de Responsabilidades

La columna "Donde vive la decisión de negocio" nunca puede ser el microservicio de IA. La lógica de negocio — transiciones de estado, bloqueos sin override, economia de XP, calculo de ponderaciones — vive en el core o en FastAPI (anti-fuga determinístico, scoring 5D, cuotas). Spring AI apenas habilita la comunicación con el modelo; nunca reemplaza la toma de decisiones.

Arquitectura

Topología Híbrida: Java + FastAPI

La arquitectura es híbrida por necesidad técnica: Spring Boot ejecuta como sidecar orquestador en la punta de inetrconexión con el ecosistema Spring Cloud (Eureka, Gateway, AMQP), mientras que FastAPI en Python ejecuta el motor de IA propiamente dicho donde se requiere determinismo puro: buffer AST en streaming, sandboxing de código, sanitización PII y scoring híbrido 5D. Ningún servicio llama directamente a un proveedor LLM; todo pasa por Gateway o RabbitMQ.

Responsabilidades

División de Responsabilidades: Java vs FastAPI

La separación entre Java y Python no es arbitraria: cada lenguaje ejecuta las tareas para las que su runtime es más eficiente. Java con Spring Boot gestiona la orquestación de servicios, el descubrimiento, el proxying SSE y la comunicación con el ecosistema Spring Cloud. Python con FastAPI ejecuta el trabajo determinístico que requiere control fino de memoria y ejecución de código: parseo AST, sanitización PII, comparación de similitud y scoring híbrido.

Justificación de la separación

Java no ejecuta el AST porque no tiene ast.parse nativo y su GC no garantiza la destrucción inmediata de buffers de código en memoria. Python no orquesta el ecosistema Spring porque no tiene clientes nativos de Eureka, RabbitMQ ni Spring AI. Cada capa corre en el lenguaje donde es natural, y se comunican por contratos HTTP/2 bien definidos.

Flujos

Flujos de Comunicación: SSE vs AMQP

Existen dos flujos de comunicación inter-servicios que reflejan dos naturalezas distintas de operación: el tutor socrático operado en streaming síncrono sobre SSE para latencia interactiva (<800ms), y el evaluador analítico operado asíncronamente sobre AMQP para procesamiento batch de alta integridad. La elección de protocolo no es decorativa: determina las garantías de entrega, la tolerancia a fallos y el modelo de responsabilidad entre microservicio y motor de desafíos.

1. Tutor Socrático en Streaming (SSE) Síncrono

El alumno escribe en el IDE Monaco y espera una respuesta en tiempo real. La respuesta debe fluir letra por letra para mantener la ilusión de un tutor presente.

  1. 1. Frontend llama a Gateway (:8080) POST /api/v1/tutor/stream
  2. 2. Gateway resuelve en Eureka y rutea al Spring Sidecar (:8081)
  3. 3. Spring WebClient hace proxy a FastAPI (:8082)
  4. 4. FastAPI verifica cuota en Redis, llama al modelo (Gemini) y pasa por Buffer AST
  5. 5. Stream SSE fluye hacia Monaco Editor en vivo (<800ms TTFT)
2. Evaluación Analítica Forense (5D) Asíncrono

El alumno entrega el desafío y la evaluación ocurre en background. No hay interacción humana esperada; la integridad del score es prioritaria sobre la latencia.

  1. 1. Alumno entrega ejercicio en Motor de Desafíos
  2. 2. Motor publica en RabbitMQ: student.challenge.submitted
  3. 3. Spring RabbitListener consume y encola en Celery Worker
  4. 4. Worker ejecuta Scoring Híbrido (código + Claude Haiku T=0)
  5. 5. Persiste en scores_ia y publica ai.evaluation.completed
Atomicidad de la Economía

Dos escritores sobre la economía (IA y Motor de Desafíos) generarían condiciones de carrera. La IA solo emite métricas pedagógicas. El evento AMQP ai.evaluation.completed es el puente entre el mundo de la evaluación y la modificación de XP que realiza el Motor de Desafíos con el factor PAR-05 (±20%).

Gobernanza de Código

SonarQube: Rationale e Integración

SonarQube se integra como capa de gobernanza de calidad de código tanto para el sidecar Java como para el motor Python. Su elección obedece a tres razones: (1) es el único servidor de análisis estático que cubre bugs, vulnerabilidades de seguridad y code smells en un solo tool, (2) se integra nativamente con el ecosistema Maven/Java del lado Spring Boot a través del sonar-maven-plugin, y (3) su modelo de Quality Gates permite parametrizar el pase o rechazo del pipeline según umbrales de cobertura, complejidad cíclomática y deuda técnica, lo cual se alinea con la filosofía de "contratos estrictos" del PRD.

El código del AntiFuga y del Buffer AST —que implementa la seguridad del sistema— debe alcanzar cobertura de tests y cero vulnerabilidades de seguridad antes de su despliegue. SonarQube convierte la política de calidad en algo medible, verificable y no negociable.

Análisis Estático

Detección de bugs, security hotspots y code smells en el código Java del sidecar y en el Python del motor. Identifica patrones problemáticos antes del despliegue.

RF-NFR
Cobertura con JaCoCo

Integración de JaCoCo para medir cobertura de código. El AntiFuga y el Buffer AST requieren cobertura mínima para aprobar el Quality Gate.

CI/CD
Quality Gates

Parámetros configurables: cobertura mínima, cero vulnerabilidades críticas, límite de deuda técnica. Webhook de retroalimentación al pipeline.

GRC
Alineación con el PRD

La calidad del código anti-fuga es una decisión de seguridad, no un adorno de ingeniería. Si el Buffer AST tiene un bug que permite pasar código con similitud ≥70%, el sistema incumple PAR-11 y exponde a la plataforma a fuga de soluciones. SonarQube convierte esta politíca de seguridad en un mínimo técnico verificable en cada pipeline de integración continua.

CI/CD

Integración CI/CD y Quality Gates

La integración de SonarQube en el pipeline de CI/CD sigue un modelo de dos etapas: análisis estático con el plugin Maven y evaluación de calidad con Quality Gates. El comando que ejecuta el pipeline completo incluye tanto la validación de código como el análisis de seguridad, asegurando que ninguna builds pase a entorno de staging sin haber superado los umbrales de calidad definidos por el equipo de ADMIN. 

mvn clean verify org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
  -Dsonar.projectKey=llm-service \
  -Dsonar.host.url=https://sonarqube.utn.edu.ar \
  -Dsonar.login=${SONAR_TOKEN} \
  -Dsonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml \
  -Dsonar.qualitygate.wait=true
Pipeline: Java Sidecar (Spring Boot)
  1. 1. Compile — Java 21 + Maven verifica que el código compila sin warnings.
  2. 2. Test + JaCoCo — Ejecuta tests de unidad; genera reporte de cobertura.
  3. 3. SonarQube Scan — Analiza bugs, security hotspots y code smells.
  4. 4. Quality Gate — Verifica cobertura mínima y cero vulnerabilidades críticas.
  5. 5. Publish — Publica el artifact y el dashboard de calidad.
Pipeline: Python FastAPI
  1. 1. Lint — Ruff verifica estilo y reglas de formato; black formatea.
  2. 2. pytest — Ejecuta tests unitarios y de integración con cobertura.
  3. 3. SonarQube Scan — Analiza complejidad cíclomática y duplicación.
  4. 4. Quality Gate — Verifica cobertura mínima y cero issues críticos.
  5. 5. Publish — Publica el artifact Docker y el dashboard de calidad.
Nota de Calidad

El parámetro -Dsonar.qualitygate.wait=true hace que el pipeline se bloquee si el Quality Gate no se cumple, sin necesidad de intervención manual. Cualquier PR que no pase el Quality Gate se marca como fallida y el equipo de ADMIN recibe notificación con el detalle de las líneas que incumplen los umbrales definidos. El anti-fuga y el buffer AST son código crítico: su coverage mínimo es del 90% y su nivel de severidad de seguridad es "Blocker".

Regla Fundamental de Responsabilidad

El microservicio de IA informa y ejecuta inferencia. El core consume datos y toma decisiones de negocio. La calibración de RF-IA-36 es bloqueante sin override: el core consulta el estado del microservicio y bloquea la transición draft→activo si no está aprobada. Ni el ADMIN puede autorizar el arranque con el set base como reemplazo.

Riesgos

Riesgos y Mitigaciones

Todo sistema que depende de modelos fundacionales y proveedores cloud externos introduce riesgos operativos, de calidad y de seguridad que deben gestionarse proactivamente. A continuación se detallan los cuatro riesgos principales del proyecto, su probabilidad de ocurrencia, su impacto potencial sobre la plataforma y la mitigación correspondiente basada en los mecanismos de resiliencia y gobernanza ya definidos en la arquitectura.

Riesgo: Falla de proveedor LLM Alto

Uno o más proveedores cloud (Groq, Cerebras, Gemini) quedan indisponibles durante un horario de alta demanda.

Probabilidad: Media · Impacto: Alto

Mitigación: Cascada de proveedores con fallback automático (RF-IA-27). Si el proveedor primario falla, se intenta el siguiente. Si todos fallan: el tutor responde sin asistencia (factor IA = 1.0 neutro) y la evaluación queda en cola diferida.

Riesgo: Drift del evaluador Medio

El proveedor cloud actualiza silenciosamente los pesos de su modelo. Un LLM que hoy califica con 80 podría mañana calificar con 65 la misma entrega.

Probabilidad: Media · Impacto: Alto

Mitigación: DriftJob mensual (Celery Beat) que re-evalía el golden set y calcula el MAE. Si MAE > 5.0 (PAR-14), activa bandera de emergencia en Redis y bloquea evaluaciones con HTTP 503.

Riesgo: Fuga de código Alto

El tutor genera código con similitud ≥70% contra la solución esperada, violando PAR-11 y entregando la solución al alumno.

Probabilidad: Baja · Impacto: Crítico

Mitigación: Triple defensa: (1) System prompt condicionado por riesgo, (2) AntiFugaService con Levenshtein + comparación AST, (3) AntiFugaAdvisor que intercepta y regenera hasta 2 reintentos. Es red de seguridad determinística.

Riesgo: Calibración no aprobada Medio

El docente no produce el golden set de su curso o la calibración no pasa PAR-14 antes de la fecha de inicio.

Probabilidad: Media · Impacto: Alto

Mitigación: CRON del core que revisa cursos en draft próximos a iniciar sin calibración y dispara notificaciones (RF-NOT-02) con una semana de margen. Sin override: el curso no se activa sin calibración aprobada (RF-IA-36).

Plan de Contingencia

Si el evaluador está caído: se acepta la entrega, se otorga XP base y el ID de sesión entra en evaluaciones_pendientes. El job procesa la cola cada 60 segundos con backoff implícito. Si después de 5 intentos sigue fallando, se marca como error. El score diferido se aplica antes del cierre del curso; si el cierre ya ocurrió, el sistema responde 409 Conflict. La IA es un amplificador, no el motor core: el motor core es la evaluación técnica del código.

Motor de IA

Responsabilidades de Python / FastAPI

El motor de IA en Python ejecuta el trabajo determinístico que requiere control fino de memoria y ejecución de código. Cada responsabilidad está aislada en un módulo independiente con contratos HTTP/2 claros. FastAPI con uvloop provee la latencia <800ms requerida para SSE en vivo mientras gestiona el parseo AST, la sanitización PII, el anti-fuga y el scoring híbrido.

1. FastAPI + uvloop

Runtime asíncrono de alto rendimiento. FastAPI con uvloop provee latencia <800ms para SSE en vivo, manejando miles de conexiones concurrentes sin bloqueo.

2. Buffer AST (ast.parse)

Parseo seguro del código del alumno. ast.parse congela el AST en memoria, lo analiza sin ejecutarlo, y lo destruye inmediatamente tras el scoring. Java no tiene equivalente nativo.

3. Harmlessness Screen (Pydantic v2)

Filtro de seguridad con validación de esquemas. Pydantic v2 valida cada payload contra esquemas restrictivos, bloqueando inyección de prompt y payloads malformados antes de llegar al modelo.

4. PII Scrubber

Sanitización de datos personales. Elimina nombres, DNI, emails y ubicaciones del contenido del alumno antes de enviarlo al LLM usando regex y NLUs ligeros.

5. XML Delimitación

Escape y delimitación de contenido. Envuelve el código del alumno entre delimitadores XML <code> para que el LLM lo trate como datos, no como instrucción.

6. Redis Anti-Crescendo

Control de momentum anti-puzzle. Ventana deslizante de 5 turnos con semáforo de 25 slots en Redis. Bloquea intentos de consulta rápida consecutivos que superen el umbral.

7. Scoring 5D Híbrido

Combinación regla + modelo. Scoring con reglas deterministas (completitud XML, longitud) y modelo LLM (coherencia, profundidad). Pesos calibrados con Golden Set.

8. Celery Workers

Procesamiento asíncrono de evaluaciones. Workers Celery con broker Redis para batch processing y retry automático sin bloquear el endpoint principal.

9. Rate Limiting + FinOps

Control de costos por cuota. Bucket4j por alumno:desafioId con límite de 50k tokens. Redis maneja contadores atómicos y TTLs. FinOps monitorea gasto por proveedor LLM.

10. Factory LLM

Abstracción de proveedor. Factoría que encapsula ChatClient de Spring AI. Permite cambiar entre Gemini Flash, GPT-4o, Claude sin modificar lógica de negocio. Fallback automático.

Arquitectura

Diagramas de Flujo de Integración

Cuatro flujos principales que ilustran la arquitectura híbrida Java + FastAPI. Cada diagrama muestra el recorrido completo de los datos desde el origen hasta el destino, pasando por las responsabilidades de cada servicio. Los ejemplos concretos ayudan a visualizar el comportamiento real del sistema.

1. Tutor Socrático (SSE) Síncrono <800ms
  1. Alumno escribe pregunta en IDE Monaco
  2. Spring Boot valida sesión y publica a RabbitMQ
  3. FastAPI consume → Buffer AST parsea → PII Scrubber sanitiza
  4. LLM genera respuesta token por token
  5. SSE stream devuelve respuesta al IDE en vivo

Ejemplo: "Cómo funciona PAR-10?" → flujo SSE de 3 tokens a <100ms con streaming letra por letra.

2. Evaluación 5D (AMQP) Asíncrono Batch
  1. Sistema cierra desafío y genera golden set
  2. Evaluador consume cola AMQP → Buffer AST valida código
  3. Anti-Fuga bloquea soluciones duplicadas
  4. Scoring 5D ejecuta evaluación con 5 dimensiones
  5. Resultado se escribe en core → SonarQube analiza

Ejemplo: Cierre de examen con 30 alumnos → evaluación batch asíncrona, 5 dimensiones (completitud, seguridad, código, diseño, innovación).

3. Anti-Fuga (Buffer AST) Seguridad
  1. Código alumno entra al buffer AST
  2. ast.parse() analiza el árbol sintáctico
  3. Detector identifica patrones de fuga
  4. Escape XML delimitación de contenido
  5. Respuesta genérica al alumno sin exposición

Ejemplo: Alumno inyecta "IGNORA instrucciones" → AST detecta patrón → respuesta: "No puedo ayudarte con eso".

4. Calibración Golden Set Admin
  1. ADMIN carga golden set (20 items)
  2. Evaluador ejecuta scoring contra respuestas esperadas
  3. DRIFT calcula desviación porcentual
  4. PAR-14 verifica tolerancia ±5%
  5. Alerta a ADMIN si excede → recalibración automática

Ejemplo: Golden set 20 items → 18 correctos (90%) → dentro de tolerancia. Si 15 correctos (75%) → alerta de deriva.
