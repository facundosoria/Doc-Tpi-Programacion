## Resumen

- Encolar (`QUEUED`), reclamar (`@Scheduled` cada 1s) y pasar a `RUNNING`: **funciona**, bien
  probado (`CalibrationMetricsTest`, `CalibrationStateMachineTest`).
- Activación en dos pasos (`activate-preview` con token de confirmación, `activate`): **funciona**.
- Una calibración activa por curso, estado consultable por otros servicios
  (`active-calibration`, `pending-evaluations`): **funciona**.
- **El hueco ya se cerró.** `CalibrationRunWorker.dispatch()`, después de `workflow.start(runId)`,
  llama a `CalibrationEvaluationRunner.run(runId)` en el mismo tick: por cada caso del golden set
  invoca [`ModelInvocationService`](../ep-02/h10.md) (función `EVALUATOR`, hoy siempre el fake),
  calcula el puntaje final por dimensión con los pesos de la rúbrica, inserta una fila en
  `calibration_case_results` y junta todos los casos para `CalibrationMetrics.assess` (sin
  tocarlo). El run cierra con `CalibrationWorkflowService.finish(runId, passed)`.
- CA3 y CA4 de la ficha (transición a `PASSED`/`FAILED` según el desvío PAR-14) **ya son
  demostrables** con el fake. CA5 (solo una calibración `PASSED` se puede activar) también, porque
  ahora sí puede existir una calibración `PASSED`.
- **Manejo de errores:** si la invocación de un caso falla (timeout, schema inválido, o cualquier
  error inesperado), el run entero cierra `FAILED` en vez de quedar `RUNNING` para siempre —
  cierra el riesgo simétrico de "un run que nunca puede fallar, solo colgarse".
- **Diferencia de alcance con la épica:** EP-04 describe calibración de **plataforma** (ADMIN) y
  de **curso** (docente); el código solo implementa la segunda. Ver la nota en la propia ficha.
