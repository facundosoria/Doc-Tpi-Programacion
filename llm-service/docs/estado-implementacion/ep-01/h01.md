# LLM-S01-H01 — ADR de arquitectura y convenciones técnicas

- **Estado:** 🔴 No existe
- **Ficha:** [`docs/historias/ep-01/h01.md`](../../historias/ep-01/h01.md)

## Qué pide

Un ADR versionado en el repo con el árbol de módulos (`api`/`application`/`domain`/
`infrastructure`/`security`/`configuration`), la tabla de variables de entorno, y una regla de
dependencias verificable (CA2, CA4).

## Qué hay en el código

- Búsqueda de `*adr*` en todo el repo: el único resultado es
  `docs/importado/especificacion-tecnica/07_REGISTRO_DE_DECISIONES_ADR.md`, material histórico
  importado ([00 · §1](../../00-fuentes-de-verdad-y-convenciones.md)) — no es el ADR de
  `llm-service` que pide esta historia.
- El árbol de paquetes **sí existe** en el código
  (`llm-service/src/main/java/.../llm/{api,application,domain,infrastructure,security,configuration}`)
  y de hecho respeta la frontera que un ADR debería fijar (`domain` verificado sin imports de
  Spring, según
  [`CORRECCIONES-SUGERIDAS.md` ítem 1](../../../llm-service/CORRECCIONES-SUGERIDAS.md)) — pero
  eso está aplicado por convención, no documentado ni verificado automáticamente (no hay
  ArchUnit en `pom.xml`).
- No hay tabla de variables de entorno en ningún documento de `llm-service/`.

## Veredicto por CA

| CA | Estado |
|---|---|
| CA1 — ADR publicado, mergeado tras PR | ❌ no existe el archivo |
| CA2 — enumera los seis paquetes y la regla de dependencias | ❌ |
| CA3 — tabla de variables de entorno | ❌ |
| CA4 — CI/revisión rechaza import de Spring en `domain` | ❌ no hay ArchUnit ni chequeo de CI para esto (la limpieza de `domain` es casual, no forzada) |
| CA5 — variable no listada bloquea el PR | ❌ no hay lista contra la cual validar |

**Nota:** que el árbol de paquetes ya respete la convención es una señal positiva para cuando se
escriba el ADR (no hay que reorganizar código), pero la historia pide el **documento** y su
verificación automática, no solo el resultado.
