# G03 — Moderación integrada (F2)

---

## Objetivo

Que los mensajes del chat real se permitan o bloqueen antes de entregarse,
con las apelaciones revisadas por un docente y una degradación acordada con
el equipo de chat; al archivar, se conserva solo la evidencia necesaria.

---

## Suposiciones y Restricciones

- **Suposiciones:**
  - El servicio de chat y el de notificaciones se comprometen a un contrato y
    una política de moderación acordada (qué hacer si algo falla) antes de
    que esta épica se integre de verdad.
  - El equipo dispone de un conjunto inicial de mensajes de ejemplo,
    etiquetados por categoría, para probar la moderación.
  - El chat nos da solo el contexto inmediato del mensaje a revisar, no el
    historial completo de la conversación.
- **Restricciones (legales / técnicas):**
  - La decisión de moderar ocurre antes de publicar el mensaje: un mensaje
    bloqueado nunca llega a mostrarse.
  - Hay reglas simples y rápidas (spam, contenido ofensivo, intentos de
    ocultar código) y un análisis más profundo que solo se usa para los
    casos dudosos.
  - Las reglas de detección nunca se filtran en los mensajes de bloqueo ni se
    pueden consultar desde afuera.
  - Solo se retiene el contexto mínimo aprobado del mensaje, nunca el
    historial completo.
  - Un mismo mensaje nunca se modera dos veces con resultados distintos.
  - Se conserva la evidencia solo el tiempo necesario según el tipo e
    importancia del incidente.
  - Si el análisis más profundo falla, se sigue moderando con las reglas
    simples y el resto se marca para revisar después; si falla todo el
    sistema de moderación, el mensaje queda pendiente — nunca se aprueba en
    automático.

---

## Criterios de Aceptación a nivel Épico

- [x] El conjunto mínimo de historias permite el flujo completo: el chat
  envía un mensaje, la moderación lo permite o lo bloquea antes de
  entregarlo y registra el incidente; un usuario apela un bloqueo, un
  docente revisa el mensaje y su contexto y resuelve, y la resolución queda
  auditada; ante una caída se aplica la política acordada y las revisiones
  pendientes se recuperan después.
- [x] Los KPIs iniciales se cumplen: el 100 % de los mensajes tiene una
  decisión antes de entregarse, y las reglas de detección nunca se filtran
  en ninguna respuesta o incidente.
- [x] No hay regresiones en: que un mensaje nunca se entregue y después se
  retire (salvo el caso explícito de revisión posterior), que no se retenga
  más contexto del aprobado, y que la moderación de un mismo mensaje sea
  siempre consistente.
- [x] Hay observabilidad: métricas de tiempos de decisión y cola de revisión
  pendiente, y alertas si el análisis profundo cae o se acumulan revisiones.
- [x] Está documentado cómo se usa: el contrato acordado con el chat y
  notificaciones, la política de qué hacer ante una caída, y el conjunto de
  mensajes de prueba con sus resultados.

## Dependencias / Impactos

- **Servicios / APIs:** el servicio de chat, el servicio de notificaciones,
  la capa interna de acceso a modelos (para el análisis más profundo).
- **Módulos afectados:** nuestro propio servicio, y la bandeja de incidentes
  en el frontend compartido.
- **Otros equipos:** chat y notificaciones (acuerdan el contrato y la
  política de caída con nosotros); producto/seguridad (aprueban los
  umbrales y la política).
- **Impacto en datos / migraciones:** se crean tablas de decisiones de
  moderación, incidentes, apelaciones y su resolución.
- **Feature toggles / flags:** la moderación se habilita cuando arranca esta
  fase del proyecto, no por si está técnicamente lista.
