# G03 — AI Gateway, modelos y resiliencia

---

## Objetivo

Que las funciones de IA no dependan de un proveedor de modelos concreto y que
cambiar de modelo sea una decisión operada y auditada — no un cambio de
código —, con cada llamada acotada en tiempo y en costo.

---

## Suposiciones y Restricciones

- **Suposiciones:**
  - Hay al menos un proveedor real disponible con presupuesto controlado para
    las pruebas que lo necesitan; el resto usa un proveedor simulado.
  - Las credenciales del proveedor se manejan fuera del repositorio.
  - Que un modelo haya existido o tenga buen precio no alcanza para
    habilitarlo: se habilita por evidencia de calidad (calibración).
- **Restricciones (legales / técnicas):**
  - Los proveedores de modelos quedan detrás de una capa interna con
    reintentos y límites de tiempo controlados, para que una demora de un
    proveedor no bloquee al resto del sistema.
  - Un único modelo evaluador activo a la vez, sin cambio automático entre
    modelos ni recálculo del pasado al cambiarlo.
  - La respuesta del modelo se valida contra un formato estricto antes de
    usarse; si no cumple, se rechaza, no se "completa".
  - El contenido del alumno y el material se le pasan al modelo como datos,
    nunca como instrucciones.
  - Hay presupuesto y cuotas por función y por período, con el gasto
    registrado.
  - Los logs nunca guardan el contenido de los pedidos ni las respuestas del
    modelo.

---

## Criterios de Aceptación a nivel Épico

- [ ] El conjunto mínimo de historias permite el flujo completo: una función
  de IA pide una respuesta, se aplican los límites de tiempo y presupuesto, se
  llama al proveedor asignado, se valida la respuesta, y se devuelve un
  resultado o un error controlado; un administrador puede cambiar el modelo
  de una función sin re-desplegar código.
- [ ] Los KPIs iniciales se cumplen: el 100 % de las llamadas a un modelo
  pasan por esta capa interna, y agregar un segundo proveedor no requiere
  cambios en las funciones que lo consumen.
- [ ] No hay regresiones en: el aislamiento entre proveedores, el rechazo de
  respuestas que no cumplen el formato esperado, y el registro de
  costo/latencia/errores de cada llamada.
- [ ] Hay observabilidad: se puede ver el consumo (tokens, costo, latencia,
  errores) por función y por período, y hay alertas cuando se agota una cuota
  o falla un proveedor.
- [ ] Está documentado cómo se usa y se opera: el catálogo de modelos
  disponibles, y qué hacer si se agota una cuota o un proveedor cae.

---

## Dependencias / Impactos

- **Servicios / APIs:** los proveedores de modelos de lenguaje (uno real, uno
  simulado para pruebas).
- **Módulos afectados:** la capa de acceso a modelos de nuestro propio
  servicio.
- **Otros equipos:** ninguno de forma directa — de esta épica depende el
  resto de las funciones de IA del producto (tutor, evaluación, calibración,
  moderación, RAG, agente).
- **Impacto en datos / migraciones:** se crean las tablas de catálogo de
  modelos y de registro de costo.
- **Feature toggles / flags:** la asignación de modelo por función es
  configuración operada, no un flag temporal.
