# Tareas SMART — LLM-S12-H01 · Apelar un mensaje que bloqueó la moderación

> **Estado:** ⚪ Borrador (flujo de reclamo formal del alumno ante falsos positivos).

### T1 — Esquema Flyway y entidad JPA para la tabla `moderation_appeals`

- **Específica:** crear la migración `V31__create_moderation_appeals_table.sql` con tabla `moderation_appeals` (`id`, `incident_id`, `user_id`, `appeal_reason`, `status`, `created_at`, `updated_at`) y restricción `UNIQUE (incident_id)`.
- **Medible:** la migración corre limpiamente y el índice único impide dos filas con el mismo `incident_id`.
- **Alcanzable:** 5 h, una persona de P3.
- **Relevante:** base de datos para almacenar el ciclo de vida de apelaciones.
- **Acotada:** 5 h · paso *dominio y migración*. **Depende de:** `LLM-S11-H01` · **Traza:** CA1, CA2.
- **Evidencia:** `V31__create_moderation_appeals_table.sql`, `ModerationAppealEntity.java`, `ModerationAppealRepository.java`.

### T2 — Endpoint `POST /moderation/v1/appeals` con validaciones de motivo y ownership

- **Específica:** implementar el controller y servicio para registrar una apelación; validar que el alumno autenticado (`X-User-Id`) sea el autor del mensaje bloqueado y que `appeal_reason` tenga entre 20 y 1000 caracteres, devolviendo `201 Created` con `appeal_id` y `status: PENDING_REVIEW`.
- **Medible:** llamadas válidas crean la entidad en estado pendiente; motivos vacíos o con < 20 caracteres devuelven `400 Bad Request`; intentos sobre incidentes de otros alumnos devuelven `403 Forbidden`.
- **Alcanzable:** 7 h, una persona de P3.
- **Relevante:** habilita el derecho de descargo del estudiante garantizando privacidad.
- **Acotada:** 7 h · paso *caso de uso*. **Depende de:** T1 · **Traza:** CA1, CA4, CA_negativo_2.
- **Evidencia:** `ModerationAppealController.java`, `ModerationAppealService.java`, `ModerationAppealControllerTest`.

### T3 — Manejo de conflicto por apelación duplicada (HTTP 409)

- **Específica:** verificar existencia previa de apelación para el `incident_id` antes de crear; si ya existe, rechazar la operación devolviendo `409 Conflict` con Problem Details RFC 7807 (`"error": "appeal_already_exists"`).
- **Medible:** un segundo `POST` para el mismo incidente devuelve `409 Conflict` y no modifica el registro previo.
- **Alcanzable:** 4 h, una persona de P3.
- **Relevante:** previene spam de reclamos o estados inconsistentes de revisión.
- **Acotada:** 4 h · paso *caso de uso*. **Depende de:** T2 · **Traza:** CA_negativo_1.
- **Evidencia:** prueba unitaria en `ModerationAppealServiceTest`.

### T4 — Endpoint de consulta `GET /moderation/v1/appeals/{appeal_id}`

- **Específica:** construir el endpoint de lectura para que el alumno consulte el estado de su apelación (`PENDING_REVIEW`, `CONFIRMED`, `REVERSED`), validando pertenencia mediante el token de usuario.
- **Medible:** responde `200 OK` con el estado y fecha de actualización; devuelve `404 Not Found` si el ID no existe y `403 Forbidden` si pertenece a otro alumno.
- **Alcanzable:** 5 h, una persona de P3.
- **Relevante:** permite la trazabilidad del reclamo desde el frontend de los estudiantes.
- **Acotada:** 5 h · paso *caso de uso*. **Depende de:** T2 · **Traza:** CA3, CA5.
- **Evidencia:** `ModerationAppealController.java`, `ModerationAppealControllerTest`.

### T5 — Suite de pruebas de integración para el flujo de apelación

- **Específica:** construir pruebas con Testcontainers que simulen el flujo completo: bloqueo previo del mensaje → alumno apela → consulta de estado pendiente → intento duplicado rechazado.
- **Medible:** la suite ejecuta y aprueba el 100% de los escenarios BDD definidos en la HU padre.
- **Alcanzable:** 5 h, una persona de P3.
- **Relevante:** asegura la robustez del circuito antes del pase a la bandeja docente.
- **Acotada:** 5 h · paso *prueba E2E*. **Depende de:** T3, T4 · **Traza:** CA1 a CA5, Escenario 1 y 2.
- **Evidencia:** `ModerationAppealIntegrationTest.java`.
