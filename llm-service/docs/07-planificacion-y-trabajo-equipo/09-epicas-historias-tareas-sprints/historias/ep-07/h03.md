## Descripción (Como / Quiero / Para)

- **Como:** sistema (tarea habilitadora — falla el criterio V de INVEST porque no tiene un usuario
  final directo)
- **Quiero:** que todas las funciones sujetas a un límite de uso avisen claramente cuánto falta
  para poder reintentar cuando se supera el límite diario configurado, y que los reintentos internos
  al proveedor esperen cada vez un poco más y se corten si el proveedor sigue fallando
- **Para:** proteger el presupuesto del proveedor de modelos y dar a quien consume el servicio la
  información suficiente para reintentar de forma controlada sin saturar el sistema

---

## Notas / Observaciones

- Las funciones sujetas a límite son: mensaje al tutor, evaluación síncrona, evaluación diferida e
  ingesta de material para consulta. Cualquier función nueva que llame al proveedor debe darse de
  alta en el mismo control.
- El uso se evalúa **antes** de llamar al proveedor. Si se supera el límite, se rechaza sin llegar
  a invocarlo.
- El aviso de límite superado indica cuántos segundos faltan hasta que se reinicia la cuota diaria
  (a la medianoche), y a qué función corresponde.
- Reintentos internos al proveedor (cuando el proveedor falla): se espera un poco más en cada
  intento sucesivo, hasta un máximo de 3 reintentos y un techo de 8 segundos de espera. Esto no
  aplica cuando el error es del propio pedido, solo cuando falla el proveedor.
- Corte automático por función: si más de la mitad de las llamadas a una función fallan en 60
  segundos, se corta esa función durante 30 segundos — todas las llamadas reciben un aviso de "no
  disponible por el momento" sin intentar contactar al proveedor, y pasado ese tiempo se prueba de
  nuevo con cautela.
- Cada vez que se avisa un límite superado o se activa un corte, queda registrado en las métricas
  de uso para que el panel de operaciones (H01) lo refleje.
- Este control se aplica de forma transversal a todas las funciones con límite, después de verificar
  identidad y permisos y antes de ejecutar la acción.
- Si el alumno que hace la llamada tiene un límite propio vigente (ver H02), se evalúan **ambos**
  límites — el de la función y el del alumno — y se aplica el que se agote primero. El aviso indica
  cuál de los dos disparó el corte.

---

## Criterios de Aceptación (CA)

- [ ] **CA1:** cuando los tokens consumidos en la función tutor alcanzan el 100 % del límite diario
  configurado, el siguiente pedido a esa función se rechaza con un aviso de límite superado que
  indica cuántos segundos faltan para poder reintentar.
- [ ] **CA2:** ese tiempo de espera indicado corresponde a la medianoche del día actual, con una
  tolerancia razonable.
- [ ] **CA3:** si el proveedor falla, el servicio reintenta hasta 3 veces esperando cada vez un poco
  más; si todos los intentos fallan, se devuelve un error controlado, nunca una respuesta exitosa
  con datos inventados.
- [ ] **CA4:** el corte automático se activa cuando más de la mitad de las llamadas a una función
  fallan en una ventana de 60 segundos; mientras está activo, los pedidos reciben un aviso de "no
  disponible" con tiempo de espera, sin intentar llamar al proveedor.
- [ ] **CA5:** después de que pasa el tiempo de espera indicado (o al iniciar una nueva ventana
  diaria), el mismo pedido se procesa correctamente si hay cuota disponible.
- [ ] **CA6:** cada aviso de límite superado queda registrado en las métricas de uso, asociado a su
  función.
- [ ] **CA7 (negativo):** si el proveedor está caído y la cuota también está superada, el servicio
  nunca responde como si hubiera tenido éxito; devuelve el error más específico entre "cuota
  superada" y "corte automático activo".
- [ ] **CA8 (negativo):** un aviso de límite superado que no indica el tiempo de espera se considera
  un defecto — la prueba de contrato lo detecta y bloquea la publicación.
- [ ] **CA9 (extensión por alumno):** si un alumno tiene un límite propio menor al de la función, el
  aviso se emite al agotarse **ese** límite (aunque la función todavía tenga cuota disponible),
  indicando que fue el límite del alumno el que se agotó.

## BDD

**Qué se prueba:** que el sistema avise claramente cuando se supera un límite de uso, que los
reintentos internos no devuelvan una respuesta exitosa cuando el proveedor está caído, y que el
sistema se recupere después del tiempo de espera.

### Escenario 1 — Cuota superada, aviso claro con tiempo de espera (camino correcto del caso de error controlado)

- **Dado:** la función tutor con un límite de 1.000 tokens por día ya consumidos en la ventana
  actual
- **Cuando:** un usuario autenticado envía un mensaje válido al tutor
- **Entonces:** el sistema rechaza el pedido con un aviso de límite superado y un tiempo de espera
  mayor a cero, sin llamar al proveedor

### Escenario 2 — Proveedor caído con reintentos, error controlado (caso que debe fallar)

- **Dado:** la función tutor con cuota disponible y el proveedor de modelos fallando en todos los
  intentos (simulado para la prueba)
- **Cuando:** un usuario autenticado envía un mensaje válido al tutor
- **Entonces:** el servicio reintenta 3 veces esperando cada vez más, y devuelve un error
  controlado — nunca una respuesta exitosa

### Escenario 3 — Pedido después de que pasa el tiempo de espera (recuperación)

- **Dado:** la función tutor que recibió un aviso de límite superado, y ya pasó a la nueva ventana
  diaria con cuota disponible
- **Cuando:** el mismo usuario envía el mismo mensaje válido
- **Entonces:** el servicio lo procesa correctamente, sin límite superado ni corte automático

---

## Prototipo

- **Qué recibe quien consume el servicio:** al superar el límite, un aviso claro de "límite
  superado" con el nombre de la función y cuánto tiempo falta para poder reintentar. Al activarse el
  corte automático, un aviso de "no disponible por el momento" con su propio tiempo de espera. En
  ambos casos, el aviso indica a qué se aplicó el corte (a la función, o al límite propio del
  alumno).

## Dependencias / Impactos

- **Servicios involucrados:** este servicio, el proveedor de modelos externo.
- **Módulos afectados:** control de cuota (nuevo), registro de funciones con límite (nuevo),
  manejo de reintentos y cortes (nuevo o extensión), agregador de métricas (extensión para
  registrar los avisos de límite y de corte).
- **Otros equipos / aprobaciones:** ninguno externo; revisión interna de arquitectura antes de
  integrar el cambio.
- **Impacto en datos:** nuevos tipos de eventos en las métricas de uso (límite superado, corte
  activado); sin impacto en datos de alumnos.
- **Riesgos:** el límite vigente se guarda en memoria por un rato corto para no consultar la base
  en cada pedido, así que un cambio de cuota puede tardar hasta un minuto en propagarse — se
  documenta y se acepta; el panel siempre muestra el límite efectivo real.
