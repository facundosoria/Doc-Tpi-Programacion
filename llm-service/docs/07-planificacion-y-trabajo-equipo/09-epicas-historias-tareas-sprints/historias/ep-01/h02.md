## Notas / Observaciones

- **Reglas de negocio:** `docker compose up` deja *healthy* PostgreSQL, `kafka-local` y `llm-service`
  (`kafka-local` entró con H07, 2026-09-18: broker local para probar sin la plataforma; el bus real es
  `event-bus:29092`). Requiere `.env` con `LLM_CREDENTIALS_MASTER_KEY` y la red externa `tpi-platform`
  (README, «Backend aislado»). Eureka/Gateway quedan explícitamente fuera de este compose (ver "Estrategia de autonomía")
  hasta que D01/Tema 11 entreguen sus módulos reales; simularlos localmente daría una falsa
  sensación de integración probada
  ([`05-servicios-docker.md`](../../../../02-arquitectura-y-plataforma/05-servicios-docker.md) §3).
  `up`, verificación de *health* y `down` están documentados en el README y funcionan.
- **Validaciones:** cada servicio del Compose define su `healthcheck`; el comando no se considera
  exitoso hasta que todos reportan *healthy*.
- **Datos obligatorios:** archivo `compose.yaml`, `.env.example` con las variables del ADR (H01),
  sección del README con los tres comandos.
- **Performance:** el entorno arranca en frío en un tiempo razonable en una notebook del equipo.
- **Seguridad:** el Compose usa credenciales de desarrollo, nunca secretos reales; el `.env` real
  está en `.gitignore`.
- **Accesibilidad:** no aplica.
- **Otros:** si falta Docker o `docker compose`, el arranque falla con un mensaje que nombra el
  requisito; no deja el entorno a medias.

## Criterios de Aceptación (CA)

- [x] **CA1:** en una máquina limpia con Docker, `docker compose up` deja todos los servicios

- [x] **CA4 (negativo):** con un puerto requerido ya ocupado, el error identifica el puerto en
  conflicto.

## BDD

**Característica:** entorno local reproducible.

### Escenario 1 — Arranque en máquina limpia

- **Dado:** una máquina con Docker y el repositorio clonado, sin otras dependencias instaladas
- **Cuando:** el desarrollador ejecuta `docker compose up`
- **Entonces:** PostgreSQL, `kafka-local` y `llm-service` quedan *healthy*; Eureka/Gateway no forman parte
  de este compose (ver "Estrategia de autonomía")
- **Y:** el desarrollador puede llamar al servicio sin instalar nada más

### Escenario 2 — Falta Docker

- **Dado:** una máquina sin Docker
- **Cuando:** el desarrollador ejecuta el comando de arranque
- **Entonces:** el comando falla e indica que Docker es un requisito, sin dejar contenedores a medias

### Escenario 3 — Puerto ocupado

- **Dado:** el puerto 5432 de PostgreSQL ya está en uso por otro proceso (escenario de debug local,
  con el overlay `compose.debug.yaml` — el compose base no publica ese puerto)
- **Cuando:** el desarrollador ejecuta `docker compose -f compose.yaml -f compose.debug.yaml up`
- **Entonces:** el arranque falla con un mensaje que nombra el puerto en conflicto

## Dependencias / Impactos

- **Servicios involucrados:** PostgreSQL, `kafka-local` y `llm-service` (los tres servicios activos en
  `compose.yaml`). Eureka/Gateway quedan fuera de este compose hasta que D01/Tema 11
  entreguen sus módulos reales.
- **Módulos afectados:** raíz del repositorio (`compose.yaml`, `compose.debug.yaml`, README).
- **Otros equipos / aprobaciones:** D01 (Gateway/Eureka de la cátedra), solo cuando publique sus
  módulos reales — hasta entonces, sin dependencia externa para este compose.
- **Impacto en datos / migraciones:** el volumen de PostgreSQL (`llm-postgres-data`) persiste entre
  reinicios (necesario para H06); verificado — sobrevive a `docker compose down` y solo se borra
  con `--volumes`.
- **Riesgos y mitigación:** divergencia con la plataforma real; se acota levantando solo lo que la
  plataforma expone y documentando cada servicio en
  [`05-servicios-docker.md`](../../../../02-arquitectura-y-plataforma/05-servicios-docker.md).
- **Estrategia de autonomía (mientras D01 no publique sus imágenes reales):** este `compose.yaml`
  **no** pinnea un Eureka Server ni un Spring Cloud Gateway de mentira. Fabricar acá esa
  infraestructura daría una falsa sensación de integración probada
  ([`05-servicios-docker.md`](../../../../02-arquitectura-y-plataforma/05-servicios-docker.md) §3;
  [`03-matriz-de-pruebas-de-infraestructura.md`](../../../../06-operacion-calidad-y-pruebas/03-matriz-de-pruebas-de-infraestructura.md),
  filas Gateway/Eureka). Lo único que vive de este lado es el cliente:
  `spring-cloud-starter-netflix-eureka-client` en el `pom.xml` y `EUREKA_URL` en `.env.example`
  (por defecto `http://localhost:8761/eureka/`). Cuando el Tema 01/11 entregue esos contenedores,
  se agregan a `compose.yaml` apuntando a su nombre de red real — no antes. La suite de pruebas de
  Gateway/Eureka se incorpora junto con esos módulos reales, no como simulación local.
