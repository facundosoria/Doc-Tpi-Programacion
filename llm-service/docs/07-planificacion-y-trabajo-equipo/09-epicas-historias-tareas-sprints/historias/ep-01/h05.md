## Descripción (Como / Quiero / Para)

- **Como:** equipo de integración (y el servicio administrativo como consumidor)
- **Quiero:** publicar el contrato del servicio y un simulador del banco de casos de referencia
- **Para:** que el servicio administrativo avance su integración sin esperar a que el servicio real
  esté listo

---

## Notas / Observaciones

- **Reglas de negocio:** el contrato publicado describe **solo** las operaciones que ya existen; el
  agregado acordado para este sprint se incorpora al contrato recién cuando el servicio
  administrativo lo aprueba.
- **Validaciones:** el contrato es válido según su propio formato; el simulador responde siempre con
  datos que cumplen ese contrato.
- **Datos obligatorios:** el contrato publicado, el agregado acordado, un comando simple para
  levantar el simulador, y dónde encontrarlo documentado.
- **Performance:** no aplica.
- **Seguridad:** el simulador nunca expone datos reales.
- **Accesibilidad:** no aplica.
- **Otros:** cualquier campo que todavía no exista se acuerda primero con el servicio administrativo
  — no se agrega al contrato «por las dudas».

## Criterios de Aceptación (CA)

- [x] **CA1:** el contrato publicado es válido y describe únicamente las operaciones ya construidas
  (crear banco de casos, crear entrada, listar, ver detalle).
- [x] **CA2:** el simulador se levanta con un comando documentado y responde según el contrato.
- [x] **CA3:** el agregado de este sprint fue revisado con el servicio administrativo y quedó
  registrado.
- [x] **CA4 (negativo):** un cambio que agrega al contrato una operación todavía no construida se
  rechaza.
- [x] **CA5 (negativo):** un campo nuevo sin acuerdo previo con el servicio administrativo bloquea la
  publicación.

## BDD

**Característica:** contrato y simulador del banco de casos de referencia para quienes lo consumen.

### Escenario 1 — El servicio administrativo integra contra el simulador

- **Dado:** el contrato y el simulador ya publicados
- **Cuando:** el servicio administrativo levanta el simulador con el comando documentado y prueba su
  integración
- **Entonces:** el simulador responde conforme al contrato y el servicio administrativo avanza sin
  necesitar el servicio real

### Escenario 2 — Operación que todavía no existe

- **Dado:** el acuerdo de publicar solo operaciones ya construidas
- **Cuando:** se intenta agregar al contrato una operación que el servicio todavía no ofrece
- **Entonces:** la revisión rechaza el cambio

### Escenario 3 — Campo no acordado

- **Dado:** un campo de respuesta que hoy no existe en el servicio
- **Cuando:** alguien intenta incluirlo en el contrato publicado
- **Entonces:** la publicación se bloquea hasta acordar ese campo con el servicio administrativo

## Dependencias / Impactos

- **Servicios involucrados:** servicio administrativo (consumidor).
- **Módulos afectados:** carpeta de contratos del servicio.
- **Otros equipos / aprobaciones:** el servicio administrativo aprueba el agregado y los campos
  nuevos.
- **Impacto en datos / migraciones:** ninguno.
- **Riesgos y mitigación:** que el contrato y lo realmente construido se desalineen; se cubre con
  pruebas de contrato en H09.
- **Estrategia de autonomía (mientras el servicio administrativo no confirme el agregado):** el
  simulador se levanta directamente a partir del contrato publicado, con un solo comando simple. El
  acuerdo pendiente con el servicio administrativo **no bloquea** tener el simulador funcionando
  (CA2): solo bloquea agregar campos nuevos al contrato (CA4/CA5), que siguen sin confirmar hasta la
  aprobación.
