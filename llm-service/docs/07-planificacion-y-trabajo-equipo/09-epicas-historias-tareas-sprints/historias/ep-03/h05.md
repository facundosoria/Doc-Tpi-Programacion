## Descripción (Como / Quiero / Para)

- **Como:** docente autorizado de un curso
- **Quiero:** crear el banco de casos de mi curso —copiando la versión base que publicó la
  plataforma, o armándolo desde cero—, cargarle casos y publicar versiones sucesivas
- **Para:** tener mi propia referencia de curso, trazable y versionada, sin que mis cambios afecten
  la base de la plataforma ni ninguna versión que ya publiqué

## Notas / Observaciones

- **Reglas de negocio:** un banco de casos de curso nace como borrador, ya sea vacío o **copiado de
  una versión base publicada por la plataforma**. Cada caso cargado incluye la conversación (con al
  menos un mensaje), el contexto del desafío, el autor y las cinco puntuaciones de referencia (0 a
  100 cada una). Al publicar, el banco de casos queda inmutable — igual que la rúbrica, ni siquiera
  se puede editar por error después.
- **Anonimización real:** antes de guardar cualquier caso (cargado a mano o importado), la
  conversación y sus datos pasan por un proceso que quita la identidad del alumno (nombre, mail) y
  limpia el texto libre. No es una promesa de diseño: ya está construido y se aplica siempre, sin
  excepción.
- **Importación masiva:** además de cargar casos uno por uno, existe una forma de cargar varios
  casos juntos desde un archivo, con **validación de cada fila** (conversación, contexto, autor y
  las cinco puntuaciones) y una regla de **todo o nada**: solo se guardan los casos si todas las
  filas del archivo resultaron válidas.
- **Borrado controlado:** un borrador sin usar se puede eliminar. Un banco de casos ya publicado,
  usado para calibrar, o vinculado a un desafío o examen **no se puede borrar**.
- **⚠️ Hueco abierto — origen de la base de plataforma.** Copiar desde la base de plataforma
  requiere que exista una versión de plataforma ya publicada, pero en esta revisión no se encontró
  ninguna forma de **crear** esa base de plataforma — solo existe el flujo por curso. Hay que
  confirmar con quien mantiene esta parte si falta esa función, si se carga de otra forma, o si la
  base de plataforma no es responsabilidad de esta historia.
- **Validaciones:** las cinco puntuaciones de referencia, cada una entre 0 y 100; conversación no
  vacía; nombre obligatorio al crear un borrador.
- **Performance:** sin llamadas a un modelo de IA; es lectura y escritura directa sobre la base de
  datos.
- **Seguridad:** igual que la rúbrica — solo un docente autorizado **de ese curso** puede operar;
  cualquier otro es rechazado.
- **Accesibilidad:** no evaluada en esta revisión.
- **Otros:** el perfil de desarrollo local usado para pruebas evita esta verificación de permisos —
  no usarlo para una demo en el ambiente compartido.

## Criterios de Aceptación (CA)

- [ ] **CA1:** un docente autorizado de su curso crea un banco de casos (vacío o copiado de una base
  publicada de plataforma) y le agrega un caso válido.
- [ ] **CA2:** publicar un banco de casos con al menos un caso lo deja publicado e inmutable; ningún
  cambio posterior tiene efecto.
- [ ] **CA3:** los datos de alumno de cada caso llegan sin identidad a la base, tanto cargados a
  mano como importados en lote.
- [ ] **CA4 (negativo):** un docente que no pertenece al curso es rechazado en cualquier acción.
- [ ] **CA5 (negativo):** un caso con puntajes de referencia incompletos o fuera de rango se
  rechaza, cargado a mano o por importación.
- [ ] **CA6 (negativo):** intentar borrar un banco de casos ya publicado, usado para calibrar, o
  vinculado a un desafío se rechaza, explicando el motivo.
- [ ] **CA7 (negativo):** un lote de importación con al menos una fila inválida no guarda ningún
  caso hasta que todas las filas queden válidas.

## BDD

**Característica:** banco de casos de curso versionado, con datos de alumno siempre anonimizados.

### Escenario 1 — Copiar la base de plataforma y publicar (camino correcto)

- **Dado:** un docente autorizado de su curso y una versión base de plataforma ya publicada
- **Cuando:** copia esa base a su curso, agrega un caso con conversación y los cinco puntajes, y
  publica
- **Entonces:** el banco de casos del curso queda publicado, con el caso incluido, sin afectar la
  base de plataforma original

### Escenario 2 — Anonimización real de un caso cargado

- **Dado:** un caso cuya conversación menciona el nombre y el mail del alumno
- **Cuando:** el docente lo carga
- **Entonces:** lo que queda guardado no contiene esos datos identificatorios

### Escenario 3 — Importación con una fila inválida

- **Dado:** un lote de importación con tres filas, una de ellas con puntajes fuera de rango
- **Cuando:** el docente valida y confirma el lote
- **Entonces:** la validación marca la fila inválida y no se guarda ningún caso hasta corregirla

### Escenario 4 — Borrado de un banco de casos en uso

- **Dado:** un banco de casos ya vinculado a una calibración
- **Cuando:** el docente intenta eliminarlo
- **Entonces:** el sistema rechaza el borrado y explica que está en uso

## Dependencias / Impactos

- **Servicios involucrados:** la plataforma, la base de datos.
- **Módulos afectados:** capas del servicio de IA (entrada, reglas de negocio, persistencia);
  pantallas de banco de casos del equipo.
- **Otros equipos / aprobaciones:** confirmar el hueco de la base de plataforma (ver nota arriba)
  con quien mantiene esta parte.
- **Impacto en datos / migraciones:** tablas propias de bancos de casos, sus versiones, casos e
  importaciones, con la inmutabilidad reforzada a nivel de base de datos.
- **Riesgos y mitigación:** si nadie crea la base de plataforma, copiar desde ella no tiene qué
  copiar y todo curso debe partir desde cero — se mitiga resolviendo el hueco antes de comprometer
  esta historia en un sprint.
