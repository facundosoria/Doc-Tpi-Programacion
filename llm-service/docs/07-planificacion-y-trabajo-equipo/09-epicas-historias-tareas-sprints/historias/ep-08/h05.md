# G03 — Que la moderación siga funcionando en modo degradado si el clasificador contextual falla

- **ID interno:** LLM-S13-H01
- **Épica:** EP-08 · Moderación integrada (F2)
- **Pareja asignada:** P3 + P2
- **Dependencias:** LLM-S11-H01 (canal de decisión), LLM-S11-H02 (detectores deterministas —
  base del modo degradado)
- **Estimación (plan):** ~24 h
- **Puntos Fibonacci:** *(a fijar en Planning Poker contra LLM-S01-H06)*
- **Tipo:** Tarea de sprint (habilitador)
- **Requisito / Contrato:** RF-CHT-09; restricción de épica "si el análisis más profundo falla,
  se sigue moderando con las reglas simples y el resto se marca para revisar después; si falla
  todo el sistema de moderación, el mensaje queda pendiente — nunca se aprueba en automático"
- **Referente de producto:** *(a completar en Planning)*

---

## Descripción (Como / Quiero / Para)

- **Como:** sistema (motor de moderación dentro de `llm-service`)
- **Quiero:** seguir decidiendo con los detectores deterministas cuando el clasificador
  contextual no está disponible, marcando como pendiente de revisión humana solo los casos que
  de verdad necesitaban el análisis más profundo
- **Para:** que una caída del clasificador contextual no bloquee todo el chat ni, al revés, deje
  pasar mensajes dudosos sin ningún control

---

## Notas / Observaciones

- **Reglas de negocio:** el orquestador de `LLM-S11-H01` intenta primero los detectores
  deterministas de `LLM-S11-H02`. Si dan `FAIL`, la decisión es `BLOCK` sin necesitar el
  clasificador contextual (ya cubierto). Si dan `PASS` pero el caso es **dudoso** (score cerca del
  umbral, o el mensaje activa una heurística de "revisar con más contexto"), normalmente se
  consulta al clasificador contextual — **esta historia define qué pasa cuando esa consulta
  falla**: el caso no se aprueba automáticamente ni se bloquea a ciegas, queda en
  `PENDING_REVIEW` con `classifier_used: "fallback"` y se encola para revisión humana.
- **Circuit-breaker del clasificador contextual:** si el clasificador falla repetidamente (mismo
  criterio que `LLM-S09-H03`: > 50 % de fallos en 60 s), el circuito abre y **todos** los casos
  dudosos van directo a `PENDING_REVIEW` sin reintentar la llamada, hasta que el circuito cierre.
- **Si falla todo el sistema de moderación** (ni los detectores deterministas responden — caso
  extremo, ej. caída del servicio completo): la decisión nunca es `ALLOW` por defecto. El
  `chat-service` recibe `PENDING` (mismo contrato que el timeout de `LLM-S11-H01`) y no publica el
  mensaje.
- **Qué tiene que incluir sí o sí:** el motivo de la degradación (`CONTEXTUAL_UNAVAILABLE` vs.
  `FULL_ENGINE_UNAVAILABLE`) en el registro de auditoría, para poder diferenciar ambos casos
  después.
- **Seguridad:** el modo degradado no relaja ningún umbral de los detectores deterministas —
  siguen siendo tan estrictos como en `LLM-S11-H02`.

---

## Criterios de Aceptación (CA)

- [x] **CA1:** con el clasificador contextual caído, un mensaje que los detectores deterministas
  marcan claramente `FAIL` sigue bloqueándose (`BLOCK`) sin necesitar el clasificador.
- [x] **CA2:** con el clasificador contextual caído, un mensaje dudoso (que normalmente pediría
  análisis contextual) queda en `PENDING_REVIEW` con `classifier_used: "fallback"`, nunca se
  aprueba automáticamente.
- [x] **CA3:** el circuit-breaker del clasificador contextual abre tras superar el umbral de
  fallos consecutivos, y mientras está abierto no se reintenta la llamada al clasificador para
  cada mensaje dudoso.
- [x] **CA4:** si falla el sistema de moderación completo (ni los detectores deterministas
  responden), la decisión es `PENDING` — nunca `ALLOW`.
- [x] **CA5:** el registro de auditoría distingue `CONTEXTUAL_UNAVAILABLE` de
  `FULL_ENGINE_UNAVAILABLE` como motivos de degradación distintos.
- [x] **CA_negativo_1:** (caso que debe fallar) un mensaje nunca se aprueba automáticamente solo
  porque el clasificador contextual no respondió — si el test de contrato detecta un `ALLOW`
  emitido en modo degradado sin que los detectores deterministas lo respalden, el build falla.

## BDD

**Qué se prueba:** que el modo degradado nunca relaje la moderación a "aprobar por defecto", y
que distinga entre caída parcial (solo contextual) y caída total del motor.

### Escenario 1 — Caso dudoso con clasificador caído (camino feliz del modo degradado)

- **Dado:** que el clasificador contextual está inaccesible (circuit breaker abierto) y un mensaje
  pasa los detectores deterministas pero queda marcado como dudoso
- **Cuando:** el orquestador procesa el mensaje
- **Entonces:** la decisión es `PENDING_REVIEW` con `classifier_used: "fallback"`, sin invocar al
  clasificador contextual

### Escenario 2 — Bloqueo determinista sigue funcionando sin el contextual (camino feliz)

- **Dado:** que el clasificador contextual está caído y un mensaje contiene spam evidente
- **Cuando:** el orquestador lo evalúa
- **Entonces:** el detector determinista de spam lo bloquea (`BLOCK`) sin necesitar el
  clasificador contextual

### Escenario 3 — Caída total del motor (caso que debe fallar)

- **Dado:** que ni los detectores deterministas responden (caída completa del motor de
  moderación)
- **Cuando:** el `chat-service` envía un mensaje para decisión
- **Entonces:** el sistema responde `PENDING`, el `chat-service` no publica el mensaje, y el
  incidente queda registrado como `FULL_ENGINE_UNAVAILABLE`
