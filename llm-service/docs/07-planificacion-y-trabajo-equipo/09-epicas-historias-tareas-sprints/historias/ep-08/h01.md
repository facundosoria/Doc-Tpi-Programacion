## Descripción (Como / Quiero / Para)

- **Como:** sistema / `chat-service` (actor técnico que envía el mensaje para decisión)
- **Quiero:** que cada mensaje del chat pase por una decisión de moderación (`ALLOW` / `BLOCK`) antes de entregarse al destinatario, con el incidente auditado y sin retener más contexto del necesario
- **Para:** garantizar que ningún mensaje bloqueado llegue a mostrarse, y que el `chat-service` tenga una decisión clara antes de publicar

---

## Notas / Observaciones

- Esta historia es un **habilitador de contrato**: el resto de las HU de EP-08 dependen de este canal establecido.
- El `chat-service` llama a `POST /moderation/v1/decisions` de forma **síncrona** con timeout configurable (default 800 ms).
- Si el timeout expira, la decisión devuelve `PENDING` (nunca `ALLOW` por defecto).
- La decisión debe ser **idempotente**: el mismo `message_id` siempre devuelve la misma decisión (o `PENDING` si aún no fue procesado).
- **Minimización de datos:** el payload de moderación solo incluye el texto del mensaje y metadatos mínimos (curso, rol del emisor, `message_id`); nunca el historial completo de la conversación.
- Las decisiones se almacenan durante el período de retención definido en LLM-S13-H02.
- El canal M2M debe autenticarse con JWT de servicio (scope `moderation:decide`).
- Los mensajes aprobados que luego sean retirados sin revisión explícita constituyen una violación del contrato.

---

## Criterios de Aceptación (CA)

- [x] **CA1:** Dado un mensaje válido enviado por `chat-service`, el endpoint `POST /moderation/v1/decisions` responde `200 OK` con `decision: ALLOW` o `decision: BLOCK` dentro de los 800 ms de timeout configurado.
- [x] **CA2:** Toda decisión emitida genera un registro de auditoría con: `message_id`, `decision`, `timestamp`, `reason_code` y `classifier_used`; sin incluir el texto completo del mensaje si la decisión es `ALLOW`.
- [x] **CA3:** Si el motor de moderación no puede resolver la decisión dentro del timeout, devuelve `decision: PENDING` y el `chat-service` **no** publica el mensaje.
- [x] **CA4:** El mismo `message_id` enviado múltiples veces devuelve siempre la misma decisión (idempotencia); el registro de auditoría no se duplica.
- [x] **CA5:** El endpoint rechaza peticiones sin JWT de servicio válido con scope `moderation:decide` con `401 Unauthorized`.
- [x] **CA_negativo_1:** (caso que debe fallar) Un mensaje con `decision: ALLOW` que luego es retirado sin pasar por una revisión explícita de moderación viola el contrato — este flujo **no debe existir** y el sistema debe registrar el intento como error de protocolo.
- [x] **CA_negativo_2:** (caso que debe fallar) El mismo `message_id` enviado dos veces con textos distintos **no** debe producir dos decisiones diferentes — el sistema debe devolver la decisión original y registrar la discrepancia como alerta.

## BDD

**Qué se prueba:** el ciclo completo de decisión de moderación antes de que `chat-service` publique un mensaje; la garantía de idempotencia; el comportamiento bajo fallo del motor.

### Escenario 1 — Decisión ALLOW en tiempo (camino feliz)

- **Dado:** que el `chat-service` tiene un JWT de servicio válido con scope `moderation:decide` y un mensaje nuevo con `message_id: "msg-001"` y texto dentro de los límites de longitud
- **Cuando:** llama a `POST /moderation/v1/decisions` con el payload mínimo requerido
- **Entonces:** el sistema responde `200 OK` con `{ "decision": "ALLOW", "message_id": "msg-001", "reason_code": "CLEAN", "latency_ms": <800 }` y el registro de auditoría queda persistido sin incluir el texto del mensaje

### Escenario 2 — Motor de moderación fuera de servicio / circuit open (caso que debe fallar)

- **Dado:** que el clasificador contextual y los detectores clásicos están inaccesibles (circuit breaker abierto)
- **Cuando:** el `chat-service` envía `POST /moderation/v1/decisions` para un mensaje nuevo
- **Entonces:** el sistema responde `200 OK` con `{ "decision": "PENDING", "message_id": "msg-002", "reason_code": "ENGINE_UNAVAILABLE" }` y el `chat-service` **no** publica el mensaje; el registro de auditoría refleja el estado `PENDING`

### Escenario 3 — Idempotencia de decisión (caso que debe fallar si se viola)

- **Dado:** que el mensaje `message_id: "msg-003"` ya tiene una decisión `BLOCK` almacenada
- **Cuando:** el `chat-service` vuelve a enviar `POST /moderation/v1/decisions` con el mismo `message_id`
- **Entonces:** el sistema devuelve exactamente la misma decisión `{ "decision": "BLOCK", "message_id": "msg-003", "reason_code": "SPAM" }` sin crear un nuevo registro de auditoría y sin iniciar una nueva evaluación

## Prototipo

**Contrato de Request / Response entre `chat-service` y `llm-service`**

```json
// REQUEST — POST /moderation/v1/decisions
// Headers: Authorization: Bearer <jwt_service_token>
//          Content-Type: application/json
{
  "message_id": "msg-001",
  "course_id":  "curso-42",
  "sender_role": "student",          // "student" | "teacher" | "system"
  "text": "Texto del mensaje a moderar (máx. 4096 chars)",
  "context_flags": {                 // metadatos mínimos, sin historial
    "thread_id": "thread-99",
    "is_reply": true
  }
}

// RESPONSE 200 OK
{
  "message_id": "msg-001",
  "decision":   "ALLOW",            // "ALLOW" | "BLOCK" | "PENDING"
  "reason_code": "CLEAN",           // "CLEAN" | "SPAM" | "OFFENSIVE" | "CODE_OBFUSCATION"
                                    // | "CONTEXTUAL_BLOCK" | "ENGINE_UNAVAILABLE"
  "classifier_used": "deterministic", // "deterministic" | "contextual" | "fallback"
  "latency_ms": 42,
  "incident_id": null               // UUID si decision == "BLOCK" | "PENDING"
}

// RESPONSE 401 — JWT inválido / scope ausente
{ "error": "unauthorized", "detail": "Missing scope: moderation:decide" }

// RESPONSE 409 — message_id ya tiene decisión con texto distinto
{ "error": "conflict", "detail": "message_id already decided with different content hash" }
```

## Dependencias / Impactos

- **Servicios involucrados:** `llm-service` (productor de decisiones), `chat-service` (consumidor), `audit-service` (registro de incidentes)
- **Módulos afectados:** `moderation/decisions`, `moderation/audit`, `auth/jwt-service`

- **Riesgos:** latencia del clasificador contextual puede exceder el timeout y degradar la experiencia de chat en tiempo real; se mitiga con la arquitectura de fallback de LLM-S13-H01
