## Descripción (Como / Quiero / Para)

- **Como:** alumno cuyo mensaje fue bloqueado por la moderación
- **Quiero:** poder apelar el bloqueo indicando por qué considero que mi mensaje era legítimo, y recibir una confirmación de que la apelación fue registrada con un identificador de seguimiento
- **Para:** tener una vía de reclamo formal cuando considero que la moderación fue un error, sin tener que contactar al soporte manualmente y pudiendo hacer seguimiento del estado de mi apelación

---

## Notas / Observaciones

- Solo se puede apelar un incidente con estado `BLOCK`; no se puede apelar un mensaje `ALLOW` ni uno `PENDING`.
- Cada `incident_id` admite **una sola apelación**; un segundo intento devuelve `409 Conflict`.
- El `appeal_reason` es obligatorio y debe tener entre 20 y 1000 caracteres; un motivo vacío o demasiado corto devuelve `400 Bad Request`.
- El alumno solo puede apelar incidentes generados por sus propios mensajes (validación por `user_id` del JWT).
- El estado inicial de una apelación es siempre `PENDING_REVIEW`.
- La apelación no modifica la decisión original; el mensaje sigue bloqueado hasta que el docente la resuelva (LLM-S12-H02).
- El alumno puede consultar el estado de su apelación vía `GET /moderation/v1/appeals/{appeal_id}`.
- Las apelaciones se retienen según la política de retención de LLM-S13-H02.

---

## Criterios de Aceptación (CA)

- [x] **CA1:** Un alumno autenticado que apela un incidente `BLOCK` de su propiedad con un motivo de entre 20 y 1000 caracteres recibe `201 Created` con `appeal_id`, `status: PENDING_REVIEW` y `created_at`.
- [x] **CA2:** La apelación queda registrada en el sistema con el `incident_id`, `user_id`, `appeal_reason` (sin el texto original del mensaje bloqueado a menos que sea necesario para la revisión) y `status: PENDING_REVIEW`.
- [x] **CA3:** El alumno puede consultar `GET /moderation/v1/appeals/{appeal_id}` y ver el estado actual (`PENDING_REVIEW`, `CONFIRMED`, `REVERSED`).
- [x] **CA4:** El endpoint valida que el `incident_id` pertenece al alumno autenticado; si pertenece a otro usuario devuelve `403 Forbidden`.
- [x] **CA5:** Si el `incident_id` no existe o no tiene estado `BLOCK`, el sistema devuelve `404 Not Found` o `422 Unprocessable Entity` según corresponda.
- [x] **CA_negativo_1:** (caso que debe fallar) Si el alumno intenta apelar el mismo `incident_id` por segunda vez, el sistema devuelve `409 Conflict` con `{ "error": "appeal_already_exists" }` — **no** se crea una segunda apelación.
- [x] **CA_negativo_2:** (caso que debe fallar) Si el campo `appeal_reason` está vacío o tiene menos de 20 caracteres, el sistema devuelve `400 Bad Request` con detalle de validación — **no** se crea la apelación.

## BDD

**Qué se prueba:** el registro de una apelación válida; el rechazo de apelaciones duplicadas; el rechazo de motivos insuficientes.

### Escenario 1 — Alumno apela exitosamente un bloqueo (camino feliz)

- **Dado:** que el alumno `user-55` tiene el JWT válido y el incidente `inc-001` en estado `BLOCK` le pertenece, y no existe ninguna apelación previa para ese incidente
- **Cuando:** envía `POST /moderation/v1/appeals` con `{ "incident_id": "inc-001", "appeal_reason": "El mensaje explicaba cómo funciona el encoding Base64 en el contexto de la clase, no intentaba ocultar código." }`
- **Entonces:** el sistema responde `201 Created` con `{ "appeal_id": "ap-UUID-001", "incident_id": "inc-001", "status": "PENDING_REVIEW", "created_at": "<timestamp>" }` y el incidente queda marcado como `HAS_APPEAL: true`

### Escenario 2 — Doble apelación del mismo incidente (caso que debe fallar)

- **Dado:** que el alumno `user-55` ya tiene una apelación `ap-UUID-001` en estado `PENDING_REVIEW` para el incidente `inc-001`
- **Cuando:** vuelve a enviar `POST /moderation/v1/appeals` con el mismo `incident_id: "inc-001"`
- **Entonces:** el sistema responde `409 Conflict` con `{ "error": "appeal_already_exists", "appeal_id": "ap-UUID-001" }` sin crear ningún registro adicional

### Escenario 3 — Motivo de apelación vacío (caso que debe fallar)

- **Dado:** que el alumno `user-55` tiene el JWT válido y el incidente `inc-002` en estado `BLOCK` le pertenece, sin apelaciones previas
- **Cuando:** envía `POST /moderation/v1/appeals` con `{ "incident_id": "inc-002", "appeal_reason": "" }`
- **Entonces:** el sistema responde `400 Bad Request` con `{ "error": "validation_error", "fields": [{ "field": "appeal_reason", "detail": "must be between 20 and 1000 characters" }] }` sin crear ningún registro
