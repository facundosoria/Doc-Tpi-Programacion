大多数人试图在错误的层级上改进AI代理。

当代理失败时，他们重写提示词。

当它再次失败时，他们添加更多指令。

> 在我们开始之前：
>
> 关注我的Substack，获取最新的AI alpha、代理工作流程和步骤指南，在它们达到X之前：`https://substack.com/@lunarresearcher`

然后他们切换模型，添加更多工具，增加上下文窗口，希望下一次运行会有不同的表现。

但许多代理失败并非推理失败。

它们是环境失败。

代理不知道哪些文件是重要的。

它在错误的地方使用了正确的工具。

它丢失了之前会话中做出的决策。

它未经检查就声称成功。

它在部分失败后重复了动作。

它有权做本应需要批准的事情。

模型不一定是问题所在。围绕模型的系统是不完整的。

那个系统是约束。

而设计它正在成为一门独立的工程学科。

约束工程是将模型智能转化为可靠工作的实践。

提示词改变了一次尝试。

约束改变每一次尝试。

本指南解释了如何构建一个。

## 1. 模型不是代理

一个模型可以进行推理、生成、比较和选择。

但代理还必须与真实环境互动。

它需要：

- 理解任务
- 找到相关上下文
- 选择和使用工具
- 保留状态
- 尊重权限
- 检查结果
- 从失败中恢复
- 证明工作已完成

模型是该系统中推理引擎。

约束是使推理运作的一切。

```text
用户请求
    |
    v
+-----------------------------+
|           约束              |
|  合同 | 上下文 | 策略        |
|  工具 | 状态   | 检查        |
|  跟踪 | 恢复                  |
+-----------------------------+
    |
    v
  模型
    |
    v
真实环境
```

图片：图片

在一个薄弱的约束下，一个强大的模型仍然是一个薄弱的代理。

它可能产生令人印象深刻的个别响应，但在长期任务、变化的环境和部分失败中，它的表现将不一致。

约束工程的目标不是从模型中消除不确定性。

它是将这种不确定性包含在一个可以观察、验证和恢复的系统内。

## 2. 从任务合同开始

大多数代理任务开始于模糊的意图：

> 改善入职流程。

这句话可能足以进行对话。

但它不足以进行自主执行。

在代理行动之前，约束应该将请求转换为任务合同。

一个有用的合同回答了五个问题：

图片：图片

- 必须存在什么结果？
- 范围内有什么？
- 什么必须不变？
- 什么证据证明完成？
- 哪些动作需要人工批准？

```yaml
objective: 减少入职流失

scope:
  - 注册流程
  - 入职分析

constraints:
  - 不要更改身份验证
  - 保留现有的移动行为

acceptance:
  - 测试通过
  - 发射分析事件
  - 屏幕截图覆盖桌面和移动

approval_required:
  - 生产部署
  - 数据库迁移
```

这改变了代理的问题：

> 我接下来应该做什么？

到：

> 哪个动作将环境推向合同结果？

没有合同，代理商优化的是可能的活动。

有了合同，它可以优化已验证的完成。

## 3. 给代理商一张地图，而不是一本手册

将整个存储库、文档集和对话历史全部放入上下文中并不是好的上下文工程。

这是上下文泛滥。

图片：图片

工具应该首先提供一个小的地图，然后让代理商在相关信息变得相关时检索详细信息。

```text
项目地图

产品规则 -> docs/product/
架构     -> docs/architecture.md
前端     -> apps/web/
后端     -> services/api/
测试     -> tests/
命令     -> docs/commands.md
发布规则 -> docs/release.md
```

这是渐进式披露：

```text
task -> 项目地图 -> 相关子系统 -> 精确文件 -> 本地指令
```

上下文应该根据任务需求扩展，而不是因为信息存在。

一个好的上下文编译器会决定：

- 总是需要什么
- 什么可以稍后检索
- 什么已经过时
- 什么可以总结
- 什么必须保持原样

目标不是最大上下文。

它是每令牌的最大信号。

## 4. 建立一个工具网关，而不是工具堆

给代理商二十个工具并不会使其变得有能耐。

它给了代理商二十种出错的方式。

图片：图片

每个工具都应该有一个清晰的合同：

```text
TOOL: edit_file

输入：路径、补丁
前提条件：路径存在；路径在允许的工作空间内
成功证据：补丁应用；返回的结果差异
失败行为：不允许部分覆盖；返回结构化错误
风险类别：可逆
```

工具应该控制工具的暴露和使用方式。

它可以：

- 隐藏不相关的工具
- 验证参数
- 限制路径和域
- 设置超时
- 使重试幂等
- 规范输出
- 对风险操作要求确认
- 返回证据，而不仅仅是“成功”

这创建了一个重要的分离：

```text
模型决定意图 -> 网关验证操作 -> 工具改变环境 -> 传感器观察结果
```

模型可以提出一个操作。

工具网关决定该操作是否足够有效以执行。

## 5. 区分大脑、双手和历史

许多脆弱的代理商将所有内容都混合到一个不断增长的记录中。

推理、工具调用、文件、决策、错误和旧观察都争夺相同上下文窗口。

一个更强大的系统将三个责任分开：

图片：图片

```text
大脑  规划、推理、选择
双手  在受控环境中执行工具
历史  存储持久事实、决策和运行状态
```

模型不需要在活动上下文中的每个原始事件。

它需要正确的当前状态。

沙盒不需要理解整个目标。

它需要安全地执行有限的操作。

会话日志不需要推理。

它需要保留当前上下文消失后的发生的事情。

这种分离使得长时间运行的代理商更容易恢复、检查和修复。

它还允许你替换一个部分而不需要重建整个系统。

## 6. 记忆必须成为持久状态

对话历史不是可靠的记忆。

它是一个事件流。

有用的记忆应该转换为显式状态。

图片：图片

至少保留四个类别：

```text
FACTS     关于环境发现的可信信息
DECISIONS 做出的选择及其背后的原因
PROGRESS  已完成、活跃、受阻和剩余的工作
LESSONS   应该改变未来行为的失败
```

例如：

```yaml
facts:
  - checkout validation lives in services/orders

decisions:
  - 重用现有的验证管道
  - reason: 避免第二个事实来源

progress:
  completed:
    - 添加了服务器端规则
  remaining:
    - 更新集成测试

lessons:
  - 本地测试命令需要 TEST_DB_URL
```

这比重放五十页的记录并希望模型注意到重要行要更有用。

存储原始历史以供审计。

编译持久状态以供执行。

## 7. 完成需要证据

一个代理说“完成”并不能证明任务已经完成。

它只是另一个模型输出。

图片：图片

完成必须由环境中的可观察变化来决定。

```text
声明                         证据
“the bug is fixed”            现在失败的测试通过
“the page works”              浏览器流程完成
“the migration is safe”       干运行和回滚通过
“the report is correct”       值与源数据匹配
“the task is complete”        每个验收检查都通过
```

工具应该首先运行最便宜的确定性检查。

```text
syntax -> types -> focused tests -> integration tests -> 视觉或语义审查 -> 人工批准
```

不要使用另一个模型，如果编译器、模式、校验和、查询或测试可以回答问题。

使用模型处理歧义。

使用代码进行管道。

模型可以建议任务已完成。

只有环境可以证明这一点。

## 8. 验证应攻击结果

工人和评估者不应有相同的目标。

工人试图创造最强的解决方案。

评估者试图找出它应该被拒绝的原因。

图片：图片

```text
worker -> 产生候选

verifier -> 检查合同
          -> 搜索缺失的案例
          -> 测试不受支持的声明
          -> 尝试破坏结果

survives -> 接受
fails    -> 返回有针对性的证据
```

这种不对称很重要。

如果你要求同一个代理在相同的情况下“双重检查其工作”，它通常会保留导致错误的假设。

有用的验证阶段应具备：

- 明确的拒绝标准
- 访问产生的工件
- 访问验收合同
- 需要时使用独立工具或新环境
- 拒绝而不修复的权限

验证不是第二意见。

它是一种尝试的证伪。

## 9. 模型提出，政策授权

某些规则永远不应该依赖于模型是否记得它们。

```text
never publish without approval
never expose a secret
never write outside the workspace
never exceed the spend cap
never mark tests passed unless they ran
```

这些不是提示建议。

它们是政策。

最安全的方案是将政策保留在推理循环之外。

图片：图片

```text
LOW RISK
读取文件、搜索、检查 -> 自动

REVERSIBLE CHANGE
编辑工作区、运行测试 -> 自动带跟踪

EXTERNAL EFFECT
发送消息、部署、购买 -> 明确批准

不可逆或敏感
删除数据，轮换凭证，全球发布 -> 硬门或禁止
```

后果越严重，门越难开。

自主性不是没有控制。

它是能够在明确执行的边界内自由操作的能力。

## 10. 恢复应针对故障类别

最常见的恢复策略是：

> 某事失败了。再试一次。

这并不是恢复。

这只是重复。

图片：图片

在选择下一步行动之前，工具应该先对故障进行分类。

```text
tool timeout              -> 带回退重试
invalid arguments         -> 修复工具调用
missing context           -> 检索特定源
failed test               -> 检查失败行为
permission denied         -> 请求批准或选择安全路径
contradictory requirements -> 升级至人工
repeated unchanged failure -> 停止循环
```

重试至少应该改变一个相关条件。

否则，系统只是在付费重复相同的失败。

一个有界代理循环看起来像这样：

```text
observe -> decide -> act -> measure -> accept -> repair -> escalate -> stop
```

每个循环都需要一个预算：

- 最大尝试次数
- 最大时间
- 最大支出
- 最大破坏范围
- 升级条件

可靠的代理知道如何继续。

他们也知道何时继续不再合理。

## 11. 指令应成为基础设施

当指令解释局部现实时，代理指令是有用的。

但仅凭指令是弱执行。

如果一条规则反复重要，将其移到堆栈下方。

```text
“use the formatter”        -> 自动运行格式化器
“do not import across layers” -> 添加架构测试
“include a migration rollback” -> 在CI中要求回滚文件
“do not modify generated files” -> 阻止写入生成路径
“cite every external claim” -> 验证引用覆盖率
```

这创建了一个指令梯子：

```text
explanation -> checklist -> template -> automated check -> enforced policy
```

尽可能将重要知识向下移动那个梯子。

提示应该解释判断。

工具应该执行不变量。

## 12. 观察运行过程，而不仅仅是最终答案

一个干净的最终工件可能隐藏了一个可怕的过程。

代理可能：

- 访问了错误的数据
- 忽略了一个失败的命令
- 两次重试外部操作
- 消耗了预期预算的十倍
- 达到了错误的原因的正确答案

你需要能够重建运行的跟踪。

```text
09:14 contract created
09:15 context source loaded: architecture.md
09:17 file edited: checkout.ts
09:18 focused test failed: duplicate coupon
09:21 implementation repaired
09:22 focused test passed
09:24 integration test passed
09:25 external deployment blocked: approval required
```

有用的跟踪记录：

- 状态转换
- 上下文源
- 工具输入和输出
- 环境变化
- 验证结果
- 重试原因
- 批准决定
- 成本和延迟

目标不是监视。

目标是局部修复。

当运行在第18步失败时，你应该能够从可信赖的检查点重新启动，而不是重放整个任务。

## 13. 每次运行都需要一个变更收据

长的代理记录难以审查。

在运行结束时，工具应该编译一个小的变更收据。

```text
OBJECTIVE 修复结账期间的重复优惠券应用。

变更
  - 检出验证逻辑
  - 专注回归测试

验证
  - 代码风格检查通过
  - 单元测试通过
  - 检出集成测试通过

未验证
  - 生产支付提供商

决策
  - 保留现有的优惠券优先级顺序

风险
  - 旧版移动客户端本地不可用

需要批准
  - 部署到预发布环境
```

收据不是模型说了什么的总结。

它是系统可以证明的总结。

这为人类提供了一个紧凑的审查表面，并为下一个代理会话提供了一个值得信赖的起点。

最好的交接不是“这是对话。”

它是“这是状态、证据和未解决风险。”

## 14. 每次失败都应提升安全带

最弱的团队修复失败的输出。

最强的团队也修复允许其发生的系统。

在失败后，问：

- 任务合同是否含糊不清？
- 重要背景是否不可见？
- 错误的工具是否暴露？
- 是否缺少先决条件？
- 结果是否可验证？
- 政策是否留在提示中？
- 恢复是否过于宽泛？
- 跟踪是否不足？

然后将教训转化为可重用的改进。

```text
failure -> diagnosis -> 新传感器、规则、地图、测试或工具合同 -> 未来运行自动改进
```

这是安全带飞轮。

系统变得更加可靠，因为失败留下了基础设施。

一个纠正的答案帮助一次运行。

一个纠正的安全带帮助每一次未来的运行。

## 15. 安全带也会退化

更多的安全带并不总是更好的。

模型改进。工具改进。任务改变。旧的安全措施可能变得不再必要。

为昨天的模型创建的解决方案可能阻止今天的模型使用更好的策略。

这导致了安全带退化：

```text
old model limitation -> harness workaround -> model improves -> workaround remains -> system becomes slower or less capable
```

将安全带组件视为生产代码。

衡量它们是否仍然提供提升。

对于每个路由器、评估器、内存层和重试规则，问：

- 这防止了哪种失败？
- 那种失败多久发生一次？
- 这增加了多少延迟和复杂性？
- 现在是否可以用更简单的方法实现相同的结果？
- 如果我们移除它会发生什么？

最好的安全带不是最大的一个。

它是能够可靠地弥合意图和证据之间差距的最小系统。

构建以删除为目标。

## 16. 最小可行安全带

您不需要编排平台就可以开始。

以分层的方式构建安全带。

第1层：一个有界任务

- 目标
- 范围
- 约束
- 接受检查

第2层：一个可读的环境

- 项目地图
- 命令
- 本地说明
- 已知依赖项

第3层：受控动作

- 类型化工具
- 参数验证
- 路径和权限边界
- 结构化结果

第4层：持久执行

- 显式的运行状态
- 检查点
- 决策
- 经验教训

第5层：证据

- 确定性检查
- 对抗性验证
- 变更收据

第6层：恢复和学习

- 失败分类
- 有限重试
- 升级
- 从重复失败中更新的安全带

构建最小的层，以消除您实际遇到的失败。

不要从多代理架构开始，因为单个提示偶尔需要澄清。

复杂性应该通过观察到的失败来获得。

## 17. 可重用安全带规范

在赋予代理有意义自主权之前，定义以下内容：

```text
铁律规范

1. 合同
   目标：
   范围：
   约束条件：
   接受证据：

2. 背景
   始终加载的地图：
   检索来源：
   本地指令：
   新鲜度规则：

3. 工具
   允许使用的工具：
   预设条件：
   副作用：
   成功证据：
   超时和重试策略：

4. 状态
   事实：
   决策：
   进展：
   经验教训：
   检查点格式：

5. 策略
   自动执行动作：
   需要批准的动作：
   禁止的动作：
   预算限制：

6. 验证
   确定性检查：
   对抗性检查：
   接受规则：

7. 恢复
   失败类别：
   重试限制：
   升级条件：
   安全回滚：

8. 可观察性
   跟踪事件：
   指标：
   最终变更接收：
```

如果这些字段未定义，则代理不是自主的。

它在即兴创作。

## 18. 在正确的层面上衡量系统

令牌计数不是最终指标。

尝试的任务数量也不是。

有用的单位是接受的工作。

一个实用的指标是：

```text
接受输出 = 人工审查分钟数 + 运行成本
```

同时跟踪：

- 首次通过接受率
- 工具失败后的恢复率
- 重复失败率
- 每个任务的人工干预
- 不受支持的完成声明
- 从请求到验证结果的时间
- 组件的 harness 负载

这可以防止一个常见的错觉：

一个代理看起来可以非常高效地工作，同时产生昂贵的审查工作。

目标是更多的代理活动，而不是更多的信任结果。

## 19. 当您不需要重型 harness 时

并非每个模型调用都需要操作系统。

当以下情况发生时使用简单的提示：

- 任务简短
- 输出易于检查
- 失败成本低
- 没有外部副作用
- 用户保持在循环中

当以下情况发生时添加 harness：

- 工作跨越多个工具或会话
- 环境可以改变
- 行动有真实后果
- 完成难以手动判断
- 相同的失败重复出现
- 人工审查成为瓶颈

harness 的目的不是让演示看起来更复杂。

它是为了使实际工作可靠。

## 真正的转变

第一代 AI 产品是围绕提示构建的。

下一代正在围绕环境构建。

问题不再是：

> 我们如何让模型回答得更好？

而是：

> 我们如何构建一个系统，其中良好的行动容易实现，危险的行为得到控制，失败可见，完成可证明？

这就是从提示工程到 harness 工程的转变。

模型提供智能。

harness 提供结构。

共同产生可靠的执行。

如果你的代理不断崩溃，停止在提示中添加形容词。

构建它成功所需的环境。
