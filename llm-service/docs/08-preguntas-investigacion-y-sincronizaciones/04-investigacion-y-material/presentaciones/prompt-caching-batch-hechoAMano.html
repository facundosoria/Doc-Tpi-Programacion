Prompt Caching + Batch API

Dos optimizaciones distintas para llamadas a LLM. Prompt Caching evita reprocesar contexto repetido. Batch API agrupa trabajos no urgentes para procesarlos de forma asíncrona y más barata.

Prompt Caching · problema

¿Qué viene a resolver?

En el evaluador, por ejemplo, podemos tener 100 alumnos. Las transcripciones cambian, pero el prompt del evaluador, la rúbrica y gran parte del contexto son iguales. Sin caching, esa parte se procesa una y otra vez.

Alumno A: [system prompt] [rúbrica] [contexto del curso] [transcripción A] Alumno B: [system prompt] [rúbrica] [contexto del curso] [transcripción B]
Sin Prompt Caching la IA sigue funcionando. El problema es que pagamos y procesamos repetidamente contenido idéntico.

¿Qué se cachea?

Se reutiliza el procesamiento de una parte repetida del prompt de entrada. No significa guardar la respuesta final.

Prompt Cacheinfra del proveedor

Nosotros armamos el prompt para que tenga una parte estable. El proveedor administra el mecanismo de caché.

Ganancia

Menor costo sobre tokens repetidos y potencialmente menor latencia.

Cuidado

No meter timestamps, IDs aleatorios o datos variables antes del prefijo estable porque disminuye la reutilización.

No confundir

Prompt Caching ≠ response caching. Redis podría guardar otros datos, pero no es el Prompt Cache del proveedor.

Batch API · problema

¿Qué viene a resolver?

Tenemos funciones donde nadie está esperando una respuesta inmediata: Evaluador, Corrector y Generador. Hacer una llamada normal por cada job funciona, pero puede ser más caro y menos eficiente.

Sin Batch: job 1 → API normal → resultado job 2 → API normal → resultado job 3 → API normal → resultado Con Batch: jobs 1..N → lote → Batch API → procesamiento async → resultados después
Batch ahorra porque aceptamos esperar. El proveedor puede procesar el lote con menos urgencia.

¿Qué significa asíncrono?

El usuario no queda bloqueado esperando la respuesta. La tarea puede completarse después.

Worker ≠ Batch API

Un worker es un proceso de fondo que toma trabajos de una cola. Puede hacer llamadas normales una por una. Eso ya es async, pero todavía no es Batch.

Async sin Batch: cola → worker → API normal Async con Batch: cola → worker agrupa N jobs → Batch API

Flujo Batch completo en nuestro llm-service

1
Se genera un job

Ej.: se cerró un intento y hay que evaluarlo.

2
El job entra a una cola

Queda pendiente sin bloquear al alumno.

3
Un worker toma varios jobs

Idealmente compatibles por función, proveedor y modelo.

4
Se crea el batch

El adapter llama a la Batch API específica del proveedor.

5
El proveedor devuelve un batch_id

Ese ID nos permite seguir el estado del lote.

6
El lote se procesa

Mientras tanto nuestro sistema puede seguir funcionando.

7
Consultamos el estado

Cuando termina, recuperamos los resultados.

8
Mapeamos cada resultado

Cada respuesta vuelve al job/alumno correcto y se guarda o publica.

Ventajas

Menor costo, mejor aprovechamiento para picos de evaluaciones y separación clara entre tareas urgentes y diferidas.

Complejidad extra

Hay que manejar estados, batch_id, errores, reintentos, duplicados y relación entre cada respuesta y su job original.
